# MOU 채팅 서버

리슨서버와 **별개의 프로세스**로 상시 가동되는 채팅/계정 서버.
호스트가 게임을 종료해도 이 프로세스는 살아있으므로 채팅 로그와 점수가 유지된다.

현재 범위는 **1~3단계**다.

| 단계 | 내용 | 상태 |
|---|---|---|
| 1 | 프로토콜 정의 (`ChatProtocol.h`) | 완료 |
| 2 | 세션 구조체 (`Session.h/.cpp`) | 완료 |
| 3 | 길이 프리픽스 프레이밍 (`Framing.h/.cpp`) | 완료 |
| 4 | 로그인 — 서버가 신원 확정 | 기본 형태만 (DB 없음) |
| 5 | 채널 라우팅 | All / Team / Dead 동작 |
| 6 | SQLite 적재 + 히스토리 조회 | 미구현 |
| 7 | 언리얼 클라이언트 (`FRunnable`) | 미구현 |
| 8 | 리슨서버 → 채팅서버 미러링 | 미구현 |
| 9 | 귓속말 | 미구현 |

프로토콜은 현재 **v6** 이다. 자세한 내용과 언리얼 연동은 `SERVER_INTEGRATION.md` 를 본다.

## 구조

```
MOU_Server/
  Shared/
    ChatProtocol.h   패킷 정의. 언리얼 클라이언트에서도 그대로 include 한다.
    Net.h            플랫폼별 소켓 API 래퍼
    Framing.h/.cpp   길이 프리픽스 프레이밍 (핵심)
  Server/
    Session.h/.cpp   ClientSession + SessionManager
    Server.cpp       accept 루프, 패킷 핸들러, 채널 라우팅
  TestClient/
    TestClient.cpp   검증용 콘솔 클라이언트
```

`ChatProtocol.h` 만 언리얼과 공유한다. `Framing.cpp` 는 `std::vector` 를 쓰므로
언리얼 쪽에서는 `TArray` 기반으로 같은 로직을 다시 구현한다 (7단계).

## 빌드

Visual Studio 2022 에 번들된 CMake 를 쓰거나, VS 에서 **폴더 열기**로 이 디렉터리를 연다.

```bash
cmake -S . -B build && cmake --build build --config Debug
```

CMake 없이 직접 컴파일하려면 개발자 명령 프롬프트에서:

```bash
cl /std:c++17 /EHsc /utf-8 /Fe:Server.exe Server\Server.cpp Server\Session.cpp Shared\Framing.cpp /IShared /IServer
```

`/utf-8` 은 소스에 한글 문자열이 있으므로 필수다.

## 실행

```bash
Server.exe 9000
```

```bash
TestClient.exe 127.0.0.1 9000 내이름
```

대화형 모드 명령:

| 명령 | 동작 |
|---|---|
| `/all` | 전체 채널로 전환 |
| `/team` | 팀 채널로 전환 |
| `/deadchan` | 사망 채널로 전환 |
| `/dead` / `/alive` | 내 생사 상태 변경 |
| `/ready` / `/unready` | 준비 상태 토글 (참여자용) |
| `/go` | 게임 시작 요청 (방장용, 전원 준비 필요) |
| `/hostready` | 리슨서버를 열었다고 신고 (방장용, `/go` 다음). 참여자는 이걸 받아야 떠난다 |
| `/q` | 종료 |

팀 ID 는 이름 길이의 홀짝으로 나뉜다. 팀 채널을 테스트하려면 이름 길이를 맞춰서 접속한다.

## 프레이밍 검증 (3종 필수 통과)

TCP 는 바이트 스트림이라 `send()` 한 번이 `recv()` 한 번으로 오지 않는다.
아래 셋이 통과해야 프레이밍이 올바른 것이다.

```bash
TestClient.exe 127.0.0.1 9000 splitter split
TestClient.exe 127.0.0.1 9000 merger merge
TestClient.exe 127.0.0.1 9000 attacker bad
```

| 테스트 | 보내는 것 | 통과 조건 |
|---|---|---|
| `split` | 패킷 1개를 1바이트씩 38회 | 서버에 메시지가 **정확히 1번** 출력 |
| `merge` | 패킷 3개를 1번의 send 로 | 서버에 메시지가 **3줄** 출력 |
| `bad` | `BodySize=999999` 위조 헤더 | `[차단]` 후 **해당 연결만** 끊김. 서버 프로세스는 생존 |

검증 완료 (2026-08-06): 3종 모두 통과.

## 설계상 중요한 결정

### 신원은 서버가 확정한다

기존 실습 코드는 클라이언트가 `"[이름] 메시지"` 형태로 이름을 붙여 보냈다.
서버는 문자열을 중계할 뿐이라 **누가 보냈는지 알 수 없고 위조도 가능**하다.

여기서는 `LoginReq` 시점에 서버가 `UserId` 를 부여하고 `ClientSession` 에 보관한다.
`ChatBroadcast` 의 `SenderUserId` / `SenderName` 은 항상 서버 보관값으로 채운다.
클라이언트가 보낸 값을 그대로 옮기지 않는다.

이게 없으면 사망자 채널이 성립하지 않는다 — 살아있는 플레이어가
"나 죽었음"이라고 주장하는 걸 막을 근거가 없기 때문이다.

### 수신자 선별은 채널별로

기존 `SendMSG()` 는 무조건 전원에게 보냈다.
`RouteChat()` 은 채널에 따라 수신자를 고른다. 귓속말은 9단계에서
`case` 하나를 추가하면 된다 — 수신자가 1명인 특수 케이스일 뿐이다.

### 종료는 shutdown → join → close 순서로

`recv()` 에 블록된 스레드가 있는 소켓을 곧바로 `closesocket()` 하면
**아직 나가지 않은 마지막 메시지가 유실된다.** 실제로 이 버그를 겪었다.

올바른 순서는:
1. `ShutdownSend()` — 남은 송신 데이터를 내보내고 FIN 전송
2. 수신 스레드가 `recv()==0` 을 보고 종료할 때까지 join
3. `CloseSocket()`

수신 스레드가 영원히 블록되지 않도록 `SO_RCVTIMEO` 를 걸고,
타임아웃은 오류가 아니라 정상으로 처리한다.

## 알려진 한계

- **`send()` 를 세션 락 안에서 호출한다.** 느린 클라이언트가 있으면 락을 오래 잡아
  전체 채팅이 지연된다. 인원이 늘면 세션별 송신 큐 + 전용 송신 스레드로 바꿔야 한다.
- **스레드를 detach 한다.** 서버 종료 시 클라이언트 스레드를 정리하지 않는다.
  개발용으로는 문제없지만, 정식 종료 절차가 필요하면 스레드 핸들을 보관해야 한다.
- **`SetDead` 를 클라이언트가 보낼 수 있다.** 테스트 편의를 위해 열어둔 것이며,
  8단계에서 리슨서버 전용 인증 연결에서만 받도록 잠가야 한다.
- **엔디안 변환이 없다.** 서버·클라이언트가 모두 x86 리틀엔디안이라는 전제다.
- **인증이 없다.** 4단계 로그인은 이름만 받는다. 비밀번호·토큰은 6단계에서.
