1. 지금은 뭘 쓰고 있나
====================================================================

EOS나 Steam 같은 외부 서비스는 아직 안 쓴다.
자체 TCP 서버(Server.exe) 하나로 채팅 / 계정 / 로비(방 목록) 전부 처리 중.

왜 자체 구현으로 시작했나:
  - 사망자 채팅 채널, 채팅 로그 영속화, 커스터마이징 데이터는
    애초에 EOS로 옮길 수 없는 기능이라 어차피 자체 서버가 필요했다.
  - 채팅 때문에 상시 프로세스가 어차피 하나 필요했고,
    거기에 계정/방 목록을 얹은 것이다. (로비 전용 서버를 새로 띄운 게 아님)
  - 외부 SDK, Epic/Steam 계정, 인터넷 연결 없이 팀 전원이 바로 돌릴 수 있다.
    EOS를 지금 붙이면 팀 전원이 Dev Portal 설정을 공유해야 하고,
    Steam은 AppID + Steam 클라이언트 실행이 전제된다.
    개발/수업 시연 단계에서는 이게 순수한 마찰이다.

객관적 근거 (데디케이트 서버가 아니라는 것):
  - 언리얼 엔진 코드가 0줄이다 (CMake + Winsock + SQLite로만 빌드)
  - 프로토콜에 게임플레이 패킷이 없다 (좌표/입력/어빌리티 물리적으로 없음)
  - 방 참여가 성사되면 클라이언트는 호스트로 직접 ClientTravel —
    그 뒤 게임 트래픽은 이 프로세스를 한 바이트도 지나가지 않는다
  - 부하가 방 개수와 무관하다 (Rooms.cpp는 메모리에 구조체만 들고 있음)

즉 우리가 만든 것은 EOS Session / Steam Lobby가 하는 일을
직접 구현한 것이지, "별도 백엔드를 새로 만들지 마라"는 피드백이
지양하라고 한 데디케이트 게임 서버가 아니다.

2. 지금 구조에서 인정하는 한계 — NAT
====================================================================

참가자는 서버가 알려준 호스트의 공인 IP:7777로 "직접" 붙는다.
호스트가 포트포워딩을 하지 않으면 공유기가 그 접속을 막는다.

  같은 공유기 / 교내망 (LAN)   → 동작함   (이번 프로젝트는 이 환경으로 확정)
  각자 집에서 인터넷으로       → 실패함   (호스트의 포트포워딩 필요)

자체 로비 서버로는 이 문제를 못 고친다. NAT 홀펀칭이나 릴레이 서버가
필요한데, 그게 정확히 EOS P2P가 제공하는 가치다.
→ 그래서 "최종 단계"에서 EOS를 붙일 계획이고, 그때 교체되는 것은
  세션 탐색 계층뿐이다.

====================================================================
3. EOS로 갈 때 최종 구조 (계획) — 전면 교체 아님, 하이브리드
====================================================================

  EOS Connect  ──▶ ProductUserId ──▶ accounts 테이블의 외부 키로 저장   (계정)
  EOS Session  ──▶ 방 목록 / 세션 탐색 / NAT 통과(P2P 홀펀칭·릴레이)   (로비)
  자체 서버    ──▶ 채팅(사망자 채널) / 채팅 로그 / 커스터마이징 데이터  (그대로 유지)

EOS로 못 옮기는 이유:

  기능                | EOS 대체 | 이유
  ---------------------|----------|----------------------------------------
  방 목록/세션 탐색     | 가능     | EOS Session
  계정 인증             | 가능     | EOS Connect
  사망자 채널           | 불가     | "죽은 사람에게만 보이는 채팅"은 게임 상태를
                        |          | 아는 쪽만 판정 가능. EOS는 누가 죽었는지 모름
  채팅 로그 영속화       | 불가     | 호스트가 나가도 남아야 함 (SQLite)
  커스터마이징 데이터    | 불가     | 계정에 묶인 게임 데이터.
                        |          | EOS Player Data Storage는 용도가 다름

4. 코드 상 교체 지점 — 이미 준비돼 있음 (ILobbyBackend, v6)
====================================================================

  UChatSubsystem            BP API / 상태 / 델리게이트   ← 백엔드를 모른다
    └─ ILobbyBackend                                    ← 교체 지점
         ├─ FSocketLobbyBackend   자체 서버 (현재 기본값)
         └─ FEOSLobbyBackend      EOS      (뼈대만 있음, 미구현)

  안 바뀌는 것: UChatSubsystem의 블루프린트 API, UMG 위젯 5종, 게임 로직 전부
  바뀌는 것  : FEOSLobbyBackend의 내용 + 설정값 한 줄

  전환 방법: Project Settings → Game → MOU Server → Lobby Backend
            또는 실행 인자 -MOULobbyBackend=EOS

함수별 매핑 (EOSLobbyBackend.h 주석):

  자체 서버 함수      | EOS API
  --------------------|--------------------------------------------------
  SendLogin/Register  | EOS_Connect_Login / EOS_Auth_Login
                       | (아이디/비번 대신 Epic 계정 또는 디바이스 ID)
  CreateRoom          | CreateSession (제목/비번은 FOnlineSessionSetting)
  RequestRoomList     | FindSessions (결과를 FMOURoomInfo로 변환)
  JoinRoom            | JoinSession (GetResolvedConnectString으로 주소 획득)
  LeaveRoom           | DestroySession / UnregisterPlayer
  SetReady            | UpdateSession의 멤버 세팅
  StartGame           | StartSession
  NotifyHostReady     | UpdateSession으로 "HostReady" 속성 갱신
                       | → 참여자가 OnSessionSettingsUpdated로 감지 (v6 그대로 필요)
  채팅 전체            | 구현 안 함 (SupportsChat() == false로 미리 차단)

방 목록 한 줄 구조 (FMOURoomInfo) — EOS로 가도 이 구조체는 그대로 유지:
  RoomId, HostUserId, Title, HostName, CurrentPlayers/MaxPlayers,
  bHasPassword, State
  ※ 호스트 IP 주소는 의도적으로 뺐다 — 목록만 보고 비번 방에 바로
    접속하는 것을 막기 위해. 주소는 JoinRoom 성공 시에만 별도로 내려온다.

붙이는 순서 (EOSLobbyBackend.h에 이미 적혀 있음):
  1. Epic Games Dev Portal에서 Product 생성, ProductId/SandboxId/ClientId 발급
  2. 플러그인 켜기: OnlineSubsystemEOS, EOSShared, SocketSubsystemEOS
  3. DefaultEngine.ini에 [/Script/OnlineSubsystemEOS.EOSSettings] 블록 작성
  4. Build.cs의 PrivateDependencyModuleNames에 OnlineSubsystem 계열 추가
  5. EOSLobbyBackend.h의 각 함수를 IOnlineSessionPtr/IOnlineIdentityPtr로 채운다
  6. 설정값을 EOS로 바꾼다 (코드 수정 없이 여기까지 오는 게 이 인터페이스의 목적)

6. 인게임 채팅(사망자 채팅)은 별도 결정 — 참고
====================================================================

인게임 채팅(죽은 사람끼리 쓰는 채팅)은 EOS든 자체 서버든
"외부 서버"를 아예 쓰지 않기로 확정 (CHAT_DESIGN.md 3절, 2026-08-24).

방장의 리슨서버 안에서 Server RPC(Reliable)로만 처리한다.
이유: 리슨서버가 "누가 죽었다"를 외부 서버에 계속 알리려면 별도의
     인증된 연결을 유지해야 하는데, 그러면 "호스트가 채팅 서버와
     끊겼을 때 게임 내 채팅이 죽는" 새 실패 모드가 생긴다.
     죽은 사람 채팅은 그 게임 안에서만 의미가 있고 기록도 필요 없어서
     외부 서버를 태울 이유가 없다.

생사 판정은 이미 있는 음성 시스템(UVoiceRouter)의 판정 함수를
그대로 재사용한다 — 새로 만들면 "채팅은 되는데 음성은 안 되는"
불일치가 생길 수 있어서다.

정리
====================================================================

지금 : 자체 서버(Server.exe) 하나로 계정/로비/채팅 전부 처리 (LAN 시연 확정)
나중 : EOS Connect(계정) + EOS Session(로비/NAT) 으로 교체,
       채팅/채팅로그/커스터마이징은 자체 서버에 그대로 남김
       (하이브리드 구성 — 전면 교체 아님)
인게임 사망자 채팅 : 어떤 백엔드를 쓰든 상관없이 리슨서버 RPC로 고정
