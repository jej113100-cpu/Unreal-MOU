## 1. 무엇을 만드는가

요구사항 세 가지다. **셋은 별개 시스템이 아니라 같은 파이프라인의 서로 다른 출구다.**

| # | 기능 | 한 줄 정의 |
|---|---|---|
| A | **근접 음성** | 내 목소리가 내 캐릭터 위치에서 3D 로 나온다. 가까운 사람만 듣는다 |
| B | **무전** | 무전기를 켠 사람끼리 거리와 무관하게 통신한다. **채널 구분 없음** |
| C | **NPC 청각** | 말하면 소음 이벤트가 발생한다. NPC 가 그걸 듣고 반응한다 |

> 위 표의 `C` 는 기능 번호다. 아래 키 바인딩의 `C` 키(근접 음소거)와는 **글자만 같고 무관하다.**

### 조작 요약 (키는 전부 변경 가능)

| 키 | 동작 | 조건 |
|---|---|---|
| **기본 상태** | **마이크 ON** (근접 오픈 마이크) | 살아있을 것 |
| `C` (토글) | 근접 발화 **음소거 ON/OFF** | 살아있을 것 |
| `Z` (토글) | **무전기 전원 ON/OFF** | 무전기를 소지할 것 |
| `X` (홀드) | **무전 송신 (PTT)** | 무전기 소지 + 전원 ON + 살아있을 것 |

> **근접 음성은 기본이 오픈 마이크다.** 게임을 시작하면 마이크가 이미 켜져 있고,
> `C` 는 그걸 껐다 켜는 토글(음소거 스위치)이다. **누르고 있어야 말하는 홀드가 아니다.**
> 근접과 무전은 조작 방식이 다르다 — 근접은 "기본 ON, 필요할 때 끔", 무전은 "기본 OFF,
> 누르는 동안만 송신". **왜 다르게 가는지는 7-1·7-3 절.**
>
> 무전기는 **들고만 있으면 아무 일도 없다.** `Z` 로 켜야 수신이 시작되고,
> 켠 상태에서 `X` 를 눌러야 송신된다. **전원과 송신을 분리한 이유는 7-3 절.**

### 이 설계의 핵심 재미 포인트

C 를 A/B 와 엮으면 규칙 하나로 게임이 만들어진다.

```
소리를 낸다 → 소음 이벤트가 발생한다 → NPC 가 찾아온다
```

여기서 파생되는 것들:

- **근접으로 말하면 내 위치가 노출된다.** 속삭이면 반경이 줄고, 소리치면 늘어난다.
- **★ 무전을 수신하면 내 무전기에서 소리가 난다.** 그 소리는 근처 플레이어에게도 들리고,
  **적대 NPC 도 듣는다.** 숨어 있는데 팀원이 무전을 치면 내가 들킨다.
- **그래서 `Z` 로 무전기를 꺼 둘 이유가 생긴다.** 무전망을 포기하고 안전을 택하는 선택.
- **인벤토리에 넣으면 반경이 줄지만, 배터리는 계속 닳는다.** 손에 안 든 무전기는
  송신이 안 되고 수신 반경도 좁아진다 — 그래도 "켜 둔 채로 넣어둘까" 는 배터리를
  걸고 하는 선택이다 (7-4 절).

> **(2026-08-20 결정) 폐기됨**: 초안에는 "죽으면서 떨어뜨린 무전기가 켜진 채로 남아
> 시체 주변을 위험지대로 만든다" 가 있었다. **NPC 를 유인하는 것은 무전기가 아니라
> 그것을 들고 있는 사람이어야 한다는 방향으로 정리됐다** — 떨어진 무전기는 자동으로
> 꺼지고, 주인 없는 무전기는 소리를 내지 않는다. 자세한 내용은 7-4절.

**이 문서의 목표는 위 규칙을 시스템으로 만드는 것이다.** 무전기 아이템 자체(모델, 인벤토리,
줍기/버리기)는 아이템 파트 담당이고, 이 문서는 **시스템이 아이템에게 요구하는 인터페이스**
(`URadioComponent`)만 정의한다.

## 2. 용어 정리 — "입이 움직인다" 는 무슨 뜻인가

초안에서 "무전이라도 입은 움직인다" 라고 썼는데 오해를 부르는 표현이라 여기서 정리한다.

**이 문서에서 "입이 움직인다" 는 비유이고, 실제로 뜻하는 것은 "소리가 난다" 하나뿐이다.**

| 표현 | 실제 의미 | 구현되는 것 |
|---|---|---|
| "말한다" / "입이 움직인다" | **소리가 발생한다** | 소음 이벤트 발행 + 근접 오디오 재생 |
| 립싱크 애니메이션 | 캐릭터 얼굴이 실제로 움직이는 연출 | **이번 범위 아님** (16절) |

즉 **얼굴 애니메이션(립싱크)은 구현하지 않는다.** 음량(RMS)이 이미 있으니 나중에
붙이고 싶으면 그 값을 그대로 애님 블루프린트에 넘기면 되지만, 지금은 고려하지 않는다.

**"무전 송신 중에도 소리가 난다" 의 의미**: 무전기에 대고 말해도 당신은 **실제로 입 밖으로
소리를 내고 있다.** 그러니 근처 사람에게 육성이 들리고, NPC 도 그 소리를 듣는다.

> **이건 무전기 전원과 아무 상관이 없다.** 무전기를 꺼도 당신이 입으로 내는 소리는 그대로 난다.
> 무전기 전원은 **기기의 송수신 기능**을 켜고 끄는 것이지, 당신의 목소리를 줄이는 장치가 아니다.
> 조용히 있고 싶으면 **말을 안 하면 된다.** 이 둘은 완전히 독립적인 축이다.

## 4. 왜 UE 내장 VoIP 를 안 쓰는가

UE 에는 이미 `OnlineSubsystem` + `UVOIPTalker` 조합의 VoIP 가 있다. 그걸 안 쓰는 이유:

| | 내장 VoIP (`UVOIPTalker` + OSS) | **직접 구현 (이 설계)** |
|---|---|---|
| 붙이는 비용 | 매우 낮음 | 높음. 캡처/인코딩/지터버퍼 직접 |
| 3D 공간화 | 됨 | 됨 |
| **소리가 폰이 아닌 액터(무전기)에서 나기** | **어려움** — 플레이어에 묶여 있다 | 됨. 무전기 액터 위치에서 재생 |
| **한 사람이 두 경로로 동시 송출** | **안 됨** | 됨 |
| **수신자별 라우팅 결정** | 뮤트 리스트 수준 | 완전 제어 |
| **음량(RMS)을 게임 로직이 읽기** | 어려움 | 캡처 단계에서 바로 나옴 |
| **AI 청각 연동** | 별도로 다시 만들어야 함 | 파이프라인에 내장 |
| OSS 의존 | `OnlineSubsystemNull` 필요, 함정 많음 | 없음 |

**결론: 직접 구현한다.**

결정적인 이유는 **"소리가 플레이어가 아니라 무전기 액터에서 나야 한다"** 는 요구다.
내장 VoIP 는 "플레이어 → 음성 스트림 1개" 모델이라, 무전기라는 별도 액터에서 소리가
나는 걸 표현할 수 없다. 거기다 C(NPC 청각)에 음량 값이 필요한데 내장 경로에서는 엔진 안에 갇혀 있다.

**단, 엔진의 `Voice` 모듈은 그대로 쓴다.** 마이크 캡처(`IVoiceCapture`)와 Opus 코덱
(`IVoiceEncoder`/`IVoiceDecoder`)은 엔진 것을 쓴다. 직접 만드는 것은 그 **위의 라우팅과 재생**이다.
Opus 를 직접 붙이거나 WASAPI 를 직접 만지는 일은 하지 않는다.

### 4-1. 빌드 설정 — **적용 완료 (2026-08-13)**

## 5. 왜 채팅서버가 아니라 리슨서버로 보내는가

기존 시스템이 채팅·로비를 별도 TCP 서버로 뺐으니 음성도 그리로 보내고 싶을 수 있다. **안 된다.**

| 근거 | 설명 |
|---|---|
| **TCP 는 음성에 부적합** | 패킷 하나가 늦으면 뒤의 것이 전부 대기한다(head-of-line blocking). 음성은 늦은 패킷을 **버리는 게** 맞다. 재전송된 200ms 전 목소리는 쓰레기다 |
| **위치가 채팅서버에 없다** | 근접 음성의 라우팅 조건은 거리다. 거리를 알려면 위치가 필요하고, 위치는 리슨서버에만 있다 |
| **AI 청각이 서버에 있다** | `UAIPerceptionSystem` 은 게임 월드(리슨서버)에서 돈다 |
| **무전기 상태가 게임 상태다** | 전원 ON/OFF, 소지 여부, 생사 = 전부 리슨서버가 권위 |

**전송은 UE 리플리케이션의 Unreliable RPC 로 한다.** 잃어버린 프레임은 그냥 잃어버린다 —
지터버퍼가 PLC(packet loss concealment)로 때운다. 이게 음성의 정상 동작이다.

## 6. 클래스 설계

파일 배치는 기존 `Chat/` 과 같은 규칙을 따른다.

```
Source/TeamProject_MOU/
  Public/Voice/                     Private/Voice/
    VoiceTypes.h                      (헤더 전용)
    VoiceCaptureSource.h              VoiceCaptureSource.cpp
    VoiceCodec.h                      VoiceCodec.cpp
    VoiceJitterBuffer.h               VoiceJitterBuffer.cpp
    VoiceSubsystem.h                  VoiceSubsystem.cpp
    VoiceStatusWidget.h               VoiceStatusWidget.cpp
    VoiceComponent.h                  VoiceComponent.cpp
    VoiceRouter.h                     VoiceRouter.cpp
    VoicePlaybackComponent.h          VoicePlaybackComponent.cpp
    VoiceSynthComponent.h             VoiceSynthComponent.cpp
    RadioComponent.h                  RadioComponent.cpp
    Radio.h                           Radio.cpp             ← ★ 무전기 아이템(AItemBase 상속)
    VoiceDebugRadio.h                 VoiceDebugRadio.cpp   ← ★ 임시(아이템 검증 끝나면 삭제)
```

> **★ `Radio.h/cpp` 가 `Item/` 이 아니라 `Voice/` 에 있는 이유.**
> 무전기 아이템은 **음성 파트가 소유한다.** 아이템 공통 동작(`AItemBase`)은
> 다른 파트 것이고 건드리지 않지만, 그것을 상속해 만든 무전기 자체는
> 무전 규칙(전원·송신 자격·배터리)이 전부라 음성 쪽에서 관리하는 편이
> 손이 덜 간다. **`Base/ItemBase.h` 는 읽기만 하고 절대 수정하지 않는다.**

| 클래스 | 부모 | 어디 사는가 | 역할 |
|---|---|---|---|
| `FVoiceCaptureSource` | (없음, 순수 클래스) | **클라 게임 스레드** ← 아래 ★ | 마이크 폴링 → 20ms 프레이밍 → RMS/VAD |
| `FMOUVoiceEncoder` | (없음, 순수 클래스) | 클라 게임 스레드 (**보내는 쪽 1개**) | PCM → Opus. 엔진 `IVoiceEncoder` 래퍼 |
| `FMOUVoiceDecoder` | (없음, 순수 클래스) | 클라 게임 스레드 (**스트림마다 1개**) | Opus → PCM. 상태가 있어 공유 불가 (14-4절 ★) |
| `UVoiceSubsystem` | `ULocalPlayerSubsystem` | 클라 게임 스레드 | 캡처 생명주기, 인코딩, 음소거(C)/루프백 상태, 마이크 감도 옵션 |

| `UVoiceRouter` | `UWorldSubsystem` | **서버 전용** | 무전기 레지스트리, 수신자 결정, 반이중 중재, 레이트 리밋, 소음 이벤트 (V6 이후) |

| `UVoiceSynthComponent` | `USynthComponent` | 클라 (폰/무전기에 부착) | 링버퍼에서 PCM 을 꺼내 오디오 렌더 스레드에 공급 |
| **`URadioComponent`** | `UActorComponent` | **무전기 아이템 액터** | 전원·손에듦 상태, 소리 반경. **아이템에 요구하는 인터페이스 전부** (V6 이후) |
| **`ARadio`** | **`AItemBase`** | 월드 (아이템 액터) | 실제 무전기 아이템. 아이템 조작(줍기/장착/드롭)을 위 컴포넌트로 옮겨준다 + 배터리 |

> **★ `FVoiceCaptureSource` 가 워커 스레드가 아니라 게임 스레드인 이유.**
> 처음에는 `FRunnable` 워커로 설계했다가 구현 중 되돌렸다. 엔진의 Windows 캡처
> 구현(`FVoiceCaptureWindows`)이 `FTSTickerObjectBase` 로 **게임 스레드 티커에서
> 자기 내부 버퍼를 채우는데, 그 버퍼에 뮤텍스가 없다.** 워커 스레드에서
> `GetVoiceData()` 를 부르면 게임 스레드와 데이터 레이스가 난다. 자세한 것은
> `VoiceCaptureSource.h` 상단 주석. 비용은 문제되지 않는다 - memcpy 와 320샘플
> RMS 산술뿐이다. **진짜 스레드 경계는 재생 쪽**(게임 → 오디오 렌더)이고
> 그건 `UVoiceSynthComponent` 의 링버퍼가 그대로 담당한다.

### 왜 `UVoiceComponent` 를 폰이 아니라 `PlayerController` 에 두는가

- **`PlayerController` 는 자기 소유 클라이언트에게 항상 relevant 하다.** 폰에 붙이면
  "멀리 있어서 relevant 하지 않은 폰" 의 RPC 가 조용히 사라진다 — **무전은 거리와 무관해야 하므로 치명적이다.**
- 폰이 죽어도 살아있다. 관전 중 UI 처리에 필요하다.

### 왜 `URadioComponent` 가 플레이어가 아니라 아이템에 붙는가

**무전기는 떨어뜨릴 수 있는 물건이기 때문이다.** 컴포넌트를 아이템 액터에 두면
소리가 나야 하는 위치가 **언제나 "이 액터 위치" 하나**로 정해진다 — 손에 들었든
가방에 넣었든 코드가 경우를 나눌 필요가 없다.

### 6-1. `ARadio` — `AItemBase` 를 어떻게 상속하는가

**무전기 아이템은 `AItemBase` 를 직접 상속한다.** `AWeaponItemBase` 가 아니다 —
무전기는 무기가 아니고, 무기 쪽 상태(`WeaponUseCount`, `Fire`, 피아식별)를 하나도
쓰지 않는다.

```
AActor
  └ AItemBase                ← 아이템 파트 소유. **읽기 전용, 수정 금지**
      ├ AWeaponItemBase        (무기 계열)
      ├ AConsumableItemBase    (소모품 계열)
      └ ★ ARadio               ← 음성 파트 소유
             └ URadioComponent (CreateDefaultSubobject 로 부착)
```

**`ARadio` 가 하는 일은 "아이템 조작을 무전 API 로 옮기는 것" 뿐이다.** 무전이
실제로 어떻게 라우팅되는지는 `URadioComponent` 와 `UVoiceRouter` 가 안다.

| `AItemBase` 의 훅 | `ARadio` 가 override 해서 하는 일 |
|---|---|
| `PickUp_Implementation` | `SetOwner(Picker)` — **없으면 클라의 Server RPC 가 버려진다**("No owning connection") |
| `OnEquipped_Implementation` | `RadioComponent->SetInHand(true)` — 송신 자격 부여. **전원은 안 건드린다** |
| `OnUnequipped_Implementation` | `SetInHand(false)` + 송신 중단. **전원은 유지**(가방 안에서도 수신) |
| `Drop_Implementation` | **전원 OFF** + `SetInHand(false)` + 소유권 해제 |
| `Throw_Implementation` | Drop 과 동일 |
| `OnUse_Implementation` | **의도적으로 비어 있다** (아래 ★) |

**`AItemBase` 에서 그대로 물려받아 쓰는 것** (건드릴 필요 없음): 물리/콜리전 토글,
`Multicast*` 동기화, `IInteractableInterface`(E키 줍기), 정보 위젯, `LastOwner` 추적.

#### ★ 왜 `OnUse`(좌클릭)를 비워 두었나

전원은 `Z`, 송신은 `X` 다. 좌클릭으로는 **두 조작 다 제대로 안 된다** — 무전기가
특이해서가 아니라 좌클릭 경로 자체의 한계다:

1. **좌클릭은 인벤토리 아이템에 닿지 않는다.** `AMainCharacter::OnUse` 는
   `CarryingComponent` 가 들고 있는 것만 호출한다(인벤토리 연동은 아직 `TODO`).
   그런데 무전기는 **가방에 넣은 채로도 켜져서 수신하고 배터리가 닳으므로**,
   가방 안의 무전기를 끌 수단이 반드시 필요하다. `Z` 는 전역키라서 된다.
2. **좌클릭에는 뗀 순간이 없다.** `UseAction` 은 `ETriggerEvent::Started` 에만
   바인딩돼 있다. PTT 는 누름과 뗌이 다 필요한데, `Completed` 를 붙이려면
   `AMainCharacter` 를 고쳐야 하고 그건 다른 파트 소유다.

그리고 `Z` 가 이미 전원을 담당하는데 좌클릭도 토글하면 중복일 뿐 아니라
**무기를 쏘려다, 문을 열려다 무전기가 켜지는** 오조작이 난다 — 이 게임에서
무전기가 켜지는 것은 곧 위치가 새는 것이다.

#### ★ `CurrentUseCount` 가 아니라 `CurrentDurability` 를 쓰는 이유

`AItemBase::CurrentUseCount` 는 **복제되지 않는다.** `CurrentDurability` 는
복제되고(`ReplicatedUsing = OnRep_CurrentDurability`) UI 갱신 훅까지 붙어 있다.
그래서 배터리는 `CurrentDurability` 를 그대로 재사용한다 — 새 변수를 만들지 않는다.

> `AWeaponItemBase` 는 같은 문제를 만나 별도 복제 변수(`WeaponUseCount`)를 팠다.
> 무전기는 이미 복제되는 쪽을 쓰면 되므로 그럴 필요가 없었다.

### 왜 `UVoiceSubsystem` 이 `LocalPlayerSubsystem` 인가

마이크는 **로컬 플레이어당 하나**다. `GameInstanceSubsystem`(채팅이 쓰는 것)으로 하면
PIE 다중 창에서 창마다 마이크를 열려고 해서 장치 경합이 난다.

> **PIE 다중 창 테스트 시 주의:** 창 두 개가 같은 물리 마이크를 열려고 한다.
> **PIE 에서는 첫 창만 캡처**하도록 막는다. 나머지 창은 재생만 검증한다.
> 진짜 양방향 테스트는 프로세스 두 개로 한다.

## 7. 파이프라인 상세

### 7-1. 캡처 (클라이언트)

```
IVoiceCapture(16kHz, mono, PCM16)
  → GetVoiceData() 로 가변 길이 바이트 회수
  → 누적 버퍼에 붙이고 320샘플(=20ms=640바이트) 단위로 잘라냄
  → 프레임마다 RMS 계산 → 0~1 정규화 → Loudness
  → VAD: Loudness < 임계값(옵션에서 조절) 이 200ms 지속되면 송신 중단
  → IVoiceEncoder::Encode → 40~80바이트
  → TQueue<FVoiceFrame> (SPSC)
```

**왜 16kHz mono 인가.** 사람 목소리 명료도는 8kHz 대역이면 충분하고(전화가 그렇다),
무전기 톤은 오히려 대역이 좁을수록 그럴듯하다. 48kHz 스테레오면 대역폭만 6배가 된다.

**VAD 는 게임 로직이기도 하다.** 무음을 안 보내면 대역폭이 줄지만, 진짜 이유는
**"지금 말하고 있는가" 가 곧 "지금 소리를 내고 있는가"** 라서 C(NPC 청각)의 입력이 되기 때문이다.
그래서 VAD 결과를 워커에서 계산해 프레임에 실어 보낸다. 게임 스레드에서 다시 계산하지 않는다.

**근접 음성은 기본이 오픈 마이크다. PTT(Push To Talk) 가 아니라 음소거 토글(`C`)이다.**

```
기본 상태 = 마이크 ON (VAD 가 무음/유음을 자동으로 가른다)
C 를 누르면 → 음소거 ON. 캡처 자체를 중단한다 (마이크를 놓는다. VAD 도 안 돈다)
C 를 다시 누르면 → 음소거 해제, 원래대로 오픈 마이크
```

> **왜 홀드가 아니라 토글인가.** 근접 음성은 팀원과 계속 대화하는 용도라 매번 키를
> 누르고 있는 게 부자연스럽다. 대신 "말 안 할 때는 내가 직접 끈다" 는 책임이 플레이어에게
> 넘어간다. **오픈 마이크 + NPC 청각 조합은 위험하다** — 잡담이나 기침이 그대로 소음
> 이벤트가 되어 "말 안 했는데 NPC 가 왔다" 는 불만이 나올 수 있다. 이 리스크는
> VAD 임계값(옵션에서 조절, 9절)과 소음 반경 튜닝(13절)으로 완화한다.
> **정말 조용히 있어야 하는 순간에는 `C` 로 직접 끄는 것**이 이 설계의 답이다.

### 7-2. 근접 음성 (기본 오픈 마이크, `C` 로 음소거)

```
서버 라우팅:
  수신자 = 발신자 위치에서 EffectiveRadius(발화모드) * 1.2 안에 있는
           살아있는 플레이어
           (1.2 배는 여유. 경계에서 뚝 끊기는 것보다 감쇠로 사라지는 게 자연스럽다)
```

재생: 발신자의 폰에 `VoiceSynthComponent` 를 붙이고 3D 공간화 + 거리 감쇠를 건다.

#### 거리 감쇠 (멀어질수록 작아지는 것) — 실제로 어떻게 설정하는가

`USynthComponent` 는 `UAudioComponent` 와 똑같이 감쇠를 지원한다. 확인된 프로퍼티:

| 프로퍼티 | 쓰임 |
|---|---|
| `AttenuationSettings` | `USoundAttenuation` 에셋 지정 ← **이 방식을 쓴다** |
| `bOverrideAttenuation` + `AttenuationOverrides` | 에셋 없이 코드로 직접 채우기 |
| `bAllowSpatialization` | 3D 로 들리게 할지 (무전기 2D 전환용) |

**에셋으로 뺀다** (`SA_Voice_Proximity`, `SA_Voice_RadioSpeaker` 2종).
코드에 숫자를 박으면 사운드 담당이 감쇠를 못 만진다. 발화 모드별로 반경만 코드에서 바꾼다.

**★ 반경이 두 개다. 이걸 하나로 착각하면 거리 계산이 전부 틀어진다.**

```
        │←─ Radius ─→│←──── FalloffDistance ────→│
   발화자 ●━━━━━━━━━━━━┿━━━━━━━━━━━━━━━━━━━━━━━━━━━┫  그 너머 = 무음
        │   음량 100%  │   100% → 0% 로 서서히 감소  │
        │←────────── 총 가청 거리 ─────────────────→│
```

| 필드 | 뜻 |
|---|---|
| `AttenuationShapeExtents.X` (Sphere Radius) | **감쇠가 시작되기 전** 구간. 여기까진 100% 음량 |
| `FalloffDistance` | 엔진 주석 그대로 *"volume attenuation 이 일어나는 거리"*. **Radius 바깥으로 추가되는 거리다** |

**따라서 `총 가청 거리 = Radius + FalloffDistance` 다.**
13절 발화 모드 표의 "근접 감쇠 반경" 은 **이 합계**를 뜻한다. 분해하면:

| 모드 | Radius (100% 구간) | FalloffDistance | **총 가청 거리** |
|---|---|---|---|
| 속삭임 | 150 (1.5m) | 350 | **500** (5m) |
| 보통 | 300 (3m) | 1200 | **1500** (15m) |
| 외침 | 500 (5m) | 2500 | **3000** (30m) |

**감쇠 곡선: `NaturalSound` + `FalloffMode = Silent`**

`EAttenuationDistanceModel` 은 `Linear / Logarithmic / Inverse / LogReverse / NaturalSound / Custom`
중에 고를 수 있다. **`NaturalSound`** 를 쓴다 — dB 기반이라 사람 귀에 가장 자연스럽다.

> **★ 함정: `FalloffMode` 기본값이 `Continues` 다.**
> 엔진 주석에 *"Continues attenuating pass falloff max"* 라고 돼 있다 —
> **가청 거리를 넘어가도 소리가 완전히 안 꺼진다.**
>
> 그런데 우리 서버는 `총 가청 거리 × 1.2` 밖의 사람에게는 **프레임을 아예 안 보낸다.**
> 이 둘이 어긋나면 **경계에서 목소리가 뚝 끊긴다** — 감쇠로 서서히 사라지는 게 아니라
> 서버가 송신을 멈추는 순간 잘린다. 제일 티나는 종류의 버그다.
>
> **`FalloffMode = Silent` 로 두어 클라 감쇠가 0 이 되는 지점과 서버 컷 지점을 맞춘다.**
> 서버의 1.2 배 여유는 이 정렬을 위한 안전 마진이다.

**같이 켜는 것 두 가지**

| 설정 | 효과 | 비용 |
|---|---|---|
| `bAttenuateWithLPF` (공기 흡수) | 멀수록 고음이 깎여 **먹먹해진다.** 거리감이 확 산다 | 싸다. **켠다** |
| `bEnableOcclusion` (차폐) | **벽 뒤 목소리가 막힌다.** 숨바꼭질 게임엔 거의 필수 | 소스마다 트레이스. 동시 발화자가 많으면 부담 |

`bEnableOcclusion` 은 켜되 **동시 발화자 수가 곧 트레이스 수**라는 걸 기억한다.
프로파일링에서 걸리면 근접만 켜고 무전기 스피커는 끄는 식으로 줄인다.

**무전기 스피커는 별도 감쇠 에셋을 쓴다.** 총 가청 거리 = `SpeakerHearRadius`(기본 1000).
근접보다 짧고, 무전기 특성상 `Radius` 를 거의 0 으로 두어 **가까이 가야만 또렷하게** 만든다.

### 7-3. 무전 (`Z` 전원 → `X` 송신)

**채널 개념이 없다.** 무전기를 켠 사람은 전부 같은 하나의 통신망에 있다.

> **왜 채널을 없앴나.** 동시 접속이 소수(한 방에 몇 명)라서 채널을 나누면 각 채널에
> 한두 명만 남아 무전이 무의미해진다. 채널 UI/조작도 추가로 필요해진다.
> **나중에 인원이 늘면 `Frequency` 하나만 추가하면 되도록** 라우팅 코드는
> "레지스트리에서 수신자 목록을 뽑는다" 형태로 짜 둔다.

**★ 전원 OFF 는 "음소거" 가 아니라 "기기 종료" 다.**

이 구분을 흐리면 구현이 통째로 틀어진다. **볼륨을 0 으로 만드는 것이 아니라, 무전망에서
완전히 빠지는 것이다.**

| | 음소거 (❌ 이렇게 만들지 말 것) | **기기 종료 (✅ 이 설계)** |
|---|---|---|
| 서버 동작 | 프레임을 계속 보냄 | **레지스트리에서 빠져 프레임이 아예 안 간다** |
| 클라 동작 | 받아 놓고 재생만 안 함 | 받을 것이 없다 |
| 대역폭 | 낭비된다 | 0 |
| 개조 클라이언트 | **들린다** (프레임이 이미 손에 있으므로) | 못 듣는다 |

`URadioComponent::SetPowered(false)` 는 **`UVoiceRouter` 레지스트리에서 자기를 제거한다.**
그 순간부터 서버는 이 무전기를 수신자 목록에 아예 넣지 않는다.

**전원 OFF 일 때 벌어지는 일 = 아무것도 없다.**
송신 ✕ / 수신 ✕ / 스피커 소리 ✕ / 그로 인한 소음 ✕. 무전기는 그냥 쇳덩이가 된다.

**왜 전원(`Z`)과 송신(`X`)을 분리하는가.** 이 분리가 게임의 핵심 선택을 만든다.

| 상태 | 수신 | 송신 | 스피커 소리 | 의미 |
|---|---|---|---|---|
| **전원 OFF** | ✕ | ✕ | ✕ | **기기가 죽어 있다. 무전망에서 완전히 빠진다** |
| 전원 ON, `X` 안 누름 | ○ | ✕ | ○ | 정보를 듣는다. **대신 내 무전기가 소리를 내서 위험하다** |
| 전원 ON + `X` 홀드 | ○ | ○ | ○ | 말한다 |

전원 하나로 합치면 "켜면 무조건 계속 송신" 이 되어 반이중 채널이 항상 점유되고,
숨 소리까지 전부 나간다. **`X` 를 눌러야 송신되는 구조라야 "지금 말할까 말까" 의 긴장이 생긴다.**

> **주의: 전원을 꺼도 내 육성은 그대로 난다**(2절). 무전기를 끄는 것은 기기를 끄는 것이지
> 내 입을 막는 것이 아니다. 근접 음성(기본 오픈 마이크, `C` 로 음소거)은 무전기 상태와
> 무관하게 항상 동작한다.

**서버 라우팅:**

```
전제 검사 (전부 서버가 재확인. 클라 주장 안 믿음):
  · 발신자가 살아있는가
  · 발신자가 무전기를 소지하고 있는가
  · 그 무전기 전원이 ON 인가

수신자 = 전원이 켜진 모든 무전기 액터 (발신자 본인 것은 제외)
         · 손에 들려 있든 바닥에 떨어져 있든 상관없다
         · 소유자가 죽었으면 그 사람에게는 안 들린다 (8절)
           단 무전기 자체는 소리를 낸다 → 소음은 발생한다
```

**★ 라우트 우선순위: 근접 > 무전.**
무전 송신 중에도 육성이 나가므로(2절), 가까이 있는 사람은 근접과 무전 **양쪽 조건에 다 걸린다.**
그대로 두면 같은 목소리가 두 번 겹쳐 들려 에코가 된다.
**수신자 한 명당 한 라우트만 보낸다** — 근접 반경 안이면 근접으로, 밖이면 무전으로.

**반이중 (half-duplex) — 동시에 한 명만**

```
서버가 "지금 송신 중인 사람" 을 1명만 허용.
  · 비어 있으면 → 점유, 송신 허용
  · 남이 점유 중이면 → 요청자에게 "채널 사용 중" 삑 소리 한 번, 프레임 폐기
  · 300ms 동안 프레임이 안 오면 점유 해제
```

무전기다운 맛도 있지만 진짜 이유는 **대역폭 상한**이다(12절). 근접은 반이중을 적용하지 않는다 —
실제로 여러 명이 동시에 말할 수 있어야 한다.

### 7-4. 무전기에서 나는 소리 ★ 밸런스의 핵심

> **★ 2026-08-20 결정으로 이 절의 내용이 바뀌었다.** 원안("떨어진 무전기가 계속
> 소리를 내 NPC 를 유인한다")은 폐기됐다. 아래는 확정된 현재 규칙이다.

무전을 **수신하면** 그 무전기 액터에서 소리가 난다. 단, **주인이 있는 무전기만
소리를 낸다** — 아무도 들고 있지 않은 무전기(바닥에 떨어진 것)는 재생도, 소음
이벤트도 발생하지 않는다. NPC 를 끌어들이는 것은 무전기가 아니라 **그것을 들고
있는 사람**이어야 한다는 방향이다.

소리는:

1. **그 무전기 주인에게 들린다** (정보 획득)
2. **주변 다른 플레이어에게도 들린다** (위치 노출)
3. **★ 적대 NPC 도 듣는다** (소음 이벤트 발생)

**손에 듦 vs 인벤토리 — 상태가 둘로 나뉜다.**

| 상태 | 송신 | 수신 | 반경 | 배터리 |
|---|---|---|---|---|
| 손에 듦 | **가능** | 가능 | 100% | 닳음 |
| 인벤토리 | 불가 | 가능 | `StowedRadiusScale` 배 | **닳음** |
| 드롭/던짐 | - | - | - | 전원 자동 OFF, 안 닳음 |

손에 들었는지는 `URadioComponent::IsInHand()`(서버 권위, 복제)로 판단한다.
부착 관계만으로는 손에 든 것과 인벤토리에 넣은 것을 구분할 수 없다 — 인벤토리에
넣어도 아이템 액터는 여전히 플레이어에 부착돼 있기 때문이다("투명한 주머니"). 그래서
아이템 쪽(`ARadio`)이 장착/해제 시점에 `SetInHand()` 를 별도로 호출해 알려준다.

**소지 개수 제한**: 두 대 이상 들고 있어도 라우터가 **홀더당 한 대만** 재생한다
(`UVoiceRouter::RouteRadio` 의 `HandledHolders`). 소지 개수 자체를 막는 것은
아이템 파트 몫이지만, 지켜지지 않아도 소리가 겹치지 않도록 라우터가 보장한다.

**반경은 에디터에서 조절할 수 있어야 한다.** `URadioComponent` 에 `EditAnywhere` 로 노출한다.

| 프로퍼티 | 뜻 | 기본값 |
|---|---|---|
| `SpeakerHearRadius` | 사람이 들을 수 있는 거리 (Attenuation 반경) | 1000 (10m) |
| `SpeakerNoiseRadius` | **NPC 가 들을 수 있는 거리** | 1200 (12m) |
| `SpeakerVolume` | 출력 음량 | 1.0 |
| `StowedRadiusScale` | 인벤토리에 있을 때 위 두 반경에 곱하는 배율 | 0.5 |

> **NPC 반경이 사람 반경보다 넓다.** 의도한 것이다.
> "나한텐 안 들렸는데 NPC 는 들었다" 가 있어야 긴장이 생긴다. 같으면 학습이 너무 쉽다.
> 이 두 값의 비율이 이 게임 난이도의 주 조절 손잡이다.

라우터와 클라 재생 경로는 `SpeakerHearRadius`/`SpeakerNoiseRadius` 를 **직접 읽지
않는다.** 반드시 `GetEffectiveHearRadius()` / `GetEffectiveNoiseRadius()` 를
거친다 — 인벤토리 감쇠가 한 곳(`URadioComponent`)에서만 계산돼야 사람이 듣는 반경과
NPC 가 듣는 반경, 클라 공간화 감쇠가 서로 어긋나지 않는다.

**드롭하면 전원이 꺼진다.** 자발적으로 놓았든(G 키) 사망·기절로 떨어졌든 구분하지
않는다 — `ARadio::Drop_Implementation`/`Throw_Implementation` 이 소유권 해제와
함께 전원을 끈다. 주인 없는 무전기가 소리를 내는 경로 자체가 없으므로, 사망 처리가
`Drop()` 을 태우지 않고 단순히 부착만 풀더라도 라우터의 "주인 없으면 재생 안 함"
검사가 2차 방어로 걸린다.

**배터리는 아이템 파트가 이미 갖고 있는 `AItemBase::CurrentDurability` 를
재사용한다.** 새 변수를 만들지 않는다 — 이미 복제되고(`OnRep_CurrentDurability`)
UI 갱신 훅도 붙어 있다. 켜져 있는 동안(손에 들었든 인벤토리에 있든) 서버 타이머로
초당 `BatteryDrainPerSecond` 만큼 깎이고, 0 이 되면 자동으로 꺼진다 — 방전도 결국
"레지스트리에서 빠지는 것" 이라 음소거가 아니라 기기 종료와 똑같이 취급된다.

**무전 필터를 소스 이펙트 체인으로 만든다.**
`USoundEffectSourcePresetChain` 에 밴드패스(300~3000Hz) → 디스토션 → (선택) 비트크러셔를 걸고
`VoiceSynthComponent` 에 지정한다. 코드로 샘플을 주무르지 않는다 — 디자이너가 에디터에서
톤을 굴릴 수 있어야 한다. **노이즈 베드와 스퀄치(시작/끝 삑) 는 별도 `UAudioComponent` 로 낸다.**
이게 있고 없고가 "무전기 같다" 의 90%다.

### 7-4-1. ★ 음량에 따른 반경 — 아날로그 (V11, 2026-08-24)

**모드(속삭임/보통/외침)가 정하는 반경은 이제 "상한" 이다.** 실제로 얼마나 크게
말했는지에 따라 그 아래로 **연속적으로** 줄어든다.

```
순간 RMS ──엔벨로프──> 스무딩된 음량 ──정규화──> 강도 0~1 ──곡선──> 배율 0.4~1.0
 (떨림)     어택 10ms                  감도 기준             지수 1.5
            릴리스 250ms                                        │
                                                    반경 = 모드 상한 x 배율
```

**왜 디지털(단계)이 아닌가.** RMS 는 한 문장 안에서도 크게 출렁인다(음절 사이
공백, 파열음). 임계값을 두고 "넘으면 큰 원" 으로 만들면 같은 톤으로 말하는
동안에도 **원이 초당 몇 번씩 왕복한다** — 플레이어는 규칙이 아니라 버그로 읽는다.
연속 함수는 단조증가라서 숫자를 몰라도 "조용히 말하면 안전하다" 가 예외 없이
성립한다. 단계 축은 이미 발화 모드가 담당하므로 중복이기도 하다.

#### ★★ 적용하는 곳과 적용하지 않는 곳

| | 배율 적용 | 이유 |
|---|---|---|
| 클라 감쇠 (실제로 들리는 거리) | **○** | 플레이어가 체감하는 지점 |
| NPC 소음 `MaxRange` | **○** | 조용히 말하면 NPC 도 가까이서만 듣는다 |
| 디버그 링 | **○** | 화면이 판정과 같아야 밸런싱이 가능하다 |
| **서버 근접 라우팅 컷** | **✕** | ★ 아래 |

**라우팅 컷을 음량으로 움직이면 안 된다.** 경계 근처 청취자가 수신자 목록에
들락날락해서 **프레임이 끊겼다 붙었다 한다** — `ProximityRoutingMargin`(1.2)과
`FalloffMode=Silent` 가 애초에 막으려고 있는 그 지직거림이다. 라우팅은 모드
상한으로 넉넉히 보내고, 조용한 소리가 멀리 안 들리게 만드는 일은 **클라 감쇠**에
맡긴다. 배율이 항상 1.0 이하라 클라 감쇠가 라우팅 컷을 넘을 수 없다.

#### ★★ 정규화는 클라이언트가 한다 — 서버는 할 수 없다

서버는 **각 플레이어의 마이크 보정값을 모른다.** 원본 RMS 를 받으면 "크게 말한
것" 과 "마이크가 센 것" 을 구분할 수 없고, 그대로 쓰면 **부스트를 켠 마이크가
공짜로 큰 원을 얻는다** — 숨는 것이 핵심인 게임에서 밸런스 붕괴다.

그래서 클라가 `NormalizeLoudness()` 로 0~1 강도를 만들어 보내고, 서버와 받는
클라는 `GetRadiusScaleFromNormalized()` 만 쓴다. **`FVoiceFrame::Loudness` 에
실려 오는 값은 원본 RMS 가 아니라 이 정규화된 강도다.**

#### ★★ 함정: 감도가 상한을 넘으면 기능이 조용히 죽는다

감도 보정은 잡음 바닥 × `CalibrationMargin`(2.0)을 기준으로 잡는다. 3.5mm
아날로그 입력처럼 잡음이 큰 마이크(피크 0.15)에서는 **기준이 0.30 이 되어
`LoudnessCeiling`(0.25)보다 높아진다.**

그러면 `NormalizeLoudness` 의 조절 구간이 0 이하가 되어 **모든 발화가 강도 1.0
으로 clamp 된다** — 속삭이든 소리치든 항상 최대 반경이다. 예외도 로그도 없이
기능만 사라져서 원인을 찾기가 매우 고약하다.

> **대응**: `MinLoudnessSpan`(0.08)과 `EnsureUsableLoudnessSpan()`. 감도를 바꾸는
> 모든 경로(`SetMicSensitivity`)에서 상한을 밀어올리고 경고를 남긴다.
> `MOU.Voice.LoudnessCurve` 로 손으로 낮게 넣는 경우도 같은 함수가 막는다.

#### 튜닝

```
MOU.Voice.LoudnessCurve                    현재 값 표시
MOU.Voice.LoudnessCurve 0.25 0.4 1.5       Ceiling / MinScale / Exponent
MOU.Voice.ShowRadius 1                     초록=사람, 빨강=NPC, 회색=모드 상한
```

디버그 링은 **모드 상한을 얇은 회색으로 같이 그린다.** 두 원의 간격이 곧 "더
크게 말하면 얼마나 커지는가" 라서, 이게 없으면 원이 작은 이유가 조용히 말해서인지
모드가 속삭임이라서인지 화면만 봐서는 구분할 수 없다.

> **★ 튜닝 값은 `MOUVoice::` 네임스페이스의 전역이다.** PIE 처럼 한 프로세스에
> 서버·클라가 같이 있을 때만 자동으로 일치한다. 데디케이티드 서버로 가면
> **양쪽에서 따로 실행해야** 하고, 안 그러면 화면의 원과 NPC 반경이 어긋난다.
> 그때는 `UDeveloperSettings` 로 빼서 서버 값을 권위로 삼아야 한다.

#### 관련 상수 (전부 `VoiceTypes.h`)

| 이름 | 기본값 | 뜻 |
|---|---|---|
| `LoudnessCeiling` | 0.25 | 여기 닿으면 배율 1.0 (모드 상한) |
| `MinRadiusScale` | 0.4 | 가장 조용할 때의 배율. **0 이 아니다** — 말했는데 아무에게도 안 들리면 고장으로 보인다 |
| `RadiusCurveExponent` | 1.5 | 클수록 조용한 구간이 넓게 펴진다 |
| `LoudnessAttackSeconds` | 0.01 | 거의 즉시. 소음은 창의 **첫 프레임**에 쏘므로 느리면 외침이 작게 보고된다 |
| `LoudnessReleaseSeconds` | 0.25 | 느리다. 짧으면 음절 사이마다 원이 펄럭인다 |
| `MinLoudnessSpan` | 0.08 | 감도와 상한 사이 최소 폭 (위 함정) |
| `RadiusScaleUpdateEpsilon` | 0.03 | 이만큼 벌어져야 감쇠를 실제로 갱신 (오디오 스레드 부하) |

#### 남아 있는 한계

**소음 보고는 0.3초 창의 첫 프레임 강도를 쓴다.** 창 중간에 목소리가 커지면 최대
0.3초 늦게 반영된다. 릴리스가 0.25초로 길어 엔벨로프가 어느 정도 피크를 물고
있으므로 실사용에서는 잘 드러나지 않지만, "속삭이다 갑자기 비명" 같은 경우
첫 보고가 과소평가될 수 있다. 문제가 되면 창 안의 최댓값을 물어 다음 창에
싣는 방식으로 바꾼다 — 지연과 맞바꾸는 선택이라 실제로 거슬릴 때 정한다.

### 7-5. NPC 청각 (서버 전용)

**이번 범위는 "소음 이벤트를 정확한 위치·크기로 발행하는 것" 까지다.**
NPC 가 그걸 받아서 어떻게 행동하는지는 **NPC 담당 팀원의 영역**이라 여기서 구현하지 않는다.
우리는 **계약(무엇을 언제 쏘는지)** 만 확정하고 넘긴다.

```cpp
UAISense_Hearing::ReportNoiseEvent(
    World,
    NoiseLocation,   // 발화자 위치 또는 무전기 액터 위치
    Loudness,        // 0~1 정규화 음량
    Instigator,      // 이 소리의 책임자
    MaxRange,        // 절대 상한 (에디터 설정값)
    Tag              // 아래 표
);
```

**★ 프레임마다 보고하면 안 된다.** 20ms 마다 쏘면 초당 50회 × 인원수의 perception 갱신이
돌아 서버가 죽는다.

```
집계 창(NoiseWindow) = 0.3초
  창의 첫 프레임에 한 번 쏘고, 남은 창 동안은 억제
  → 초당 3.3회
```

> **구현 시 바뀐 점 (V8):** 원안은 "창 안의 최댓값을 모아 창이 **끝날 때** 보고"였다.
> 아래 Loudness 결정으로 최댓값을 취할 의미가 사라졌고, 끝에 몰아 쏘면 두 가지가 나빴다:
> 말하기 시작하고 NPC 반응까지 0.3초가 밀리고, 0.3초보다 짧은 발화("헉!")가 통째로 누락된다.
> 보고 빈도는 그대로이므로 **첫 프레임 즉시 발행 + 억제**로 바꿨다.

#### ★ Loudness 는 1.0 고정이다 — 엔진 동작 주의

`UAISense_Hearing::Update` 는 Loudness 를 **음량이 아니라 반경 배율로 쓴다**(엔진 소스):

```cpp
if (DistSq > HearingRangeSq * Square(Loudness))            continue;  // 리스너 설정에도 곱해진다
else if (MaxRange > 0 && DistSq > Square(MaxRange * Loudness)) continue;
```

모드별 배율(0.35 / 1.0 / 1.6)을 그대로 넣으면 13절 반경표가 그만큼 어긋나고,
NPC 에디터의 `듣기 범위` 까지 같이 축소·확대된다. 그래서 `NoiseEventLoudness = 1.0` 으로
고정하고 거리는 `GetNoiseRange()` 만으로 표현한다. 그러면 판정이 이렇게 단순해진다:

```
실제로 들리는 거리 = min(NPC 의 듣기 범위, GetNoiseRange(발화모드))
```

속삭임과 외침의 차이는 **반경으로만** 낸다(700 vs 4000). NPC 입장에서
"가까이서만 들리는 소리 = 작은 소리" 이므로 표현력에 손해가 없다.

**보고 지점 (NPC 팀원에게 넘기는 계약)**

| 지점 | 위치 | Loudness | Tag | 조건 |
|---|---|---|---|---|
| 근접 발화 | 발화자 | 프레임 최대 RMS × 발화모드 배율 | `Voice.Proximity` | 살아있을 때 |
| 무전 송신 | 발화자 | **× 0.35 로 감쇠** | `Voice.Radio` | 무전이라도 육성은 난다(2절) |
| **무전 수신** | **무전기 액터** | `SpeakerVolume` × 0.8 | `Voice.RadioSpeaker` | 전원 ON. **떨어진 무전기 포함** |

> **`Instigator` 를 잘못 넣으면 NPC 가 엉뚱한 사람을 쫓는다.**
> 소음의 책임자 = **소리가 난 위치에 있는 대상**이다.
> 무전 수신 소음의 책임자는 송신자가 아니라 **그 무전기(또는 그 소유자)** 다.

**NPC 팀원이 할 일** (이 문서 범위 밖, 인터페이스만 명시):
`AIPerceptionComponent` 에 `AISenseConfig_Hearing` 을 추가하고, 위 Tag 로 반응을 분기한다.

> #### ★★ 함정: 지금은 `아군 탐지`를 켜야 들린다 ★★
>
> 현재 프로젝트에 `IGenericTeamAgentInterface` 구현이 **하나도 없다.** 그래서 NPC 도
> 플레이어도 팀이 `NoTeam(255)` 이다. 엔진의 기본 판정은 이렇다:
>
> ```cpp
> // AIInterfaces.cpp — DefaultTeamAttitudeSolver
> return A != B ? ETeamAttitude::Hostile : ETeamAttitude::Friendly;
> ```
>
> `255 == 255` 라서 **플레이어는 NPC 에게 "아군"** 으로 분류된다. 중립이 아니다.
> `AISenseConfig_Hearing` 의 `Detection by Affiliation` 에서 **`아군 탐지`** 를 켜야
> 목소리가 들린다. `중립 탐지` 만 켜면 아무리 가까워도 안 들린다.
>
> 팀을 제대로 배정하면(`AAIController::SetGenericTeamId` + 플레이어 폰에
> `IGenericTeamAgentInterface` 구현) `적 탐지` 로 정리된다. **NPC 담당자 영역.**
>
> 참고로 `FGenericTeamId::GetAttitude(액터, 액터)` 오버로드는 상대가 인터페이스를
> 구현하지 않으면 무조건 `Neutral` 을 돌려준다. 퍼셉션이 쓰는 것은 TeamId 오버로드라
> 결과가 다르다 — 디버깅할 때 이 둘을 섞으면 원인을 못 찾는다.

**★ NPC 팀원이 우리를 기다리지 않게 하는 장치:**
`MOU.Voice.FakeNoise <반경>` 콘솔 명령을 **V1 에 가장 먼저 만든다.**
마이크도, 음성 파이프라인도 없이 소음 이벤트만 쏠 수 있어서 NPC 작업을 병렬로 할 수 있다.

## 8. 사망자 처리

**죽으면 음성으로 아무것도 못 한다.** 말할 수도, 들을 수도 없다.

| | 살아있음 | **사망** |
|---|---|---|
| 근접 발화 (오픈 마이크) | ○ | **✕** |
| 무전 송신 (`X`) | ○ | **✕** |
| 근접 청취 | ○ | **✕** |
| 무전 청취 | ○ | **✕** |
| 소음 발생 | ○ | **✕** |

**세 겹으로 막는다.** 한 겹만 두면 반드시 뚫린다.

1. **클라이언트**: 사망 상태면 캡처 자체를 중단한다 (마이크를 놓는다)
2. **서버 (송신)**: 사망자가 보낸 프레임은 라우팅 전에 폐기한다 ← **진짜 방어선**
3. **서버 (수신)**: 수신자 목록을 만들 때 사망자를 제외한다

1번만 있으면 개조 클라이언트가 계속 말할 수 있고, 3번만 있으면 사망자가 남의 대화를 엿듣는다.

**떨어뜨린 무전기는 예외다.** 주인이 죽어도 무전기 액터는 살아서 켜져 있으므로
**계속 수신하고 계속 소리를 낸다.** 다만 그 소리를 듣는 것은 **주변의 살아있는 사람과 NPC** 이지
죽은 주인이 아니다. 죽은 사람 화면에는 아무 소리도 나지 않는다.

### 8-1. 사망자 채팅 (검토 중)

**살아있는 동안에는 텍스트 채팅이 없다.** 음성만 쓴다 — 채팅창을 보느라 화면에서
눈을 떼는 순간 공포 게임의 긴장이 사라지기 때문이다.

**죽은 뒤에만 죽은 사람들끼리 텍스트 채팅**을 여는 것을 검토 중이다. 관전 시간이 지루하지
않게 하는 장치다.

> **좋은 소식: 이건 이미 만들어져 있다.**
> 기존 채팅 시스템에 **`Dead` 채널이 이미 있다** (`EChatChannelBP::Dead`).
> 서버가 사망자에게만 라우팅하는 것도 구현돼 있다.
> **필요한 작업은 "살아있을 때 채팅 UI 를 숨기고, 죽으면 Dead 채널로 띄우는 것" 뿐이다.**
>
> 단 `SERVER_INTEGRATION.md` 11절의 한계가 남아있다 — 생사 여부를
> **클라이언트가 스스로 신고**(`SetDeadForTest`)하고 있어서 위조가 가능하다.
> **8단계(리슨서버 → 채팅서버 신원 미러링)를 먼저 해야** 산 사람이 사망자 채널을
> 엿보는 것을 막을 수 있다. 음성의 생사 판정과 같은 문제라 **한 번에 같이 처리하는 게 좋다.**

## 9. 옵션 (음성 감도 등)

마이크 환경은 사람마다 천차만별이라(기계식 키보드 소리, 선풍기, 룸메이트) **감도 조절이 없으면
누군가는 반드시 못 쓴다.** 게임 옵션 화면에 넣는다.

| 옵션 | 범위 | 설명 |
|---|---|---|
| **마이크 감도** | 0.0 ~ 1.0 | VAD 임계값. **입력 게이지를 같이 보여준다** |
| 입력 장치 | 목록 | 마이크가 여러 개인 사람용 |
| 출력 음량 (음성) | 0 ~ 100% | 게임 사운드와 별도 |
| 마이크 모드 | 오픈 마이크(고정) / PTT | **기본 오픈 마이크**. PTT 는 대안으로 열어둠 |
| 키 바인딩 | — | `C`(근접 음소거) / `Z`(무전 전원) / `X`(무전 송신) 전부 변경 가능 |

**★ 감도 슬라이더 옆에 실시간 입력 게이지를 반드시 같이 둔다.**
숫자만 있으면 아무도 못 맞춘다. 말하면서 막대가 임계선을 넘는지 눈으로 봐야 조절할 수 있다.
캡처 단계에서 RMS 를 이미 계산하므로 **추가 비용이 사실상 없다.**

저장은 `UGameUserSettings` 파생 클래스나 `USaveGame` 에 한다. 키 바인딩은 EnhancedInput 의
`UEnhancedInputUserSettings` 를 쓰면 리매핑 UI 를 엔진이 거의 다 해준다.

## 10. 패킷 / 데이터 구조

```cpp
// VoiceTypes.h

UENUM(BlueprintType)
enum class EVoiceRoute : uint8
{
    Proximity  UMETA(DisplayName = "근접"),
    Radio      UMETA(DisplayName = "무전"),
};

UENUM(BlueprintType)
enum class EVoiceMode : uint8
{
    Whisper  UMETA(DisplayName = "속삭임"),
    Normal   UMETA(DisplayName = "보통"),
    Shout    UMETA(DisplayName = "외침"),
};

/** 클라 → 서버. 20ms 한 조각. */
USTRUCT()
struct FVoiceFrame
{
    GENERATED_BODY()

    UPROPERTY() uint16          Seq = 0;        // 지터버퍼 정렬용. 순환해도 무방
    UPROPERTY() EVoiceRoute     Route = EVoiceRoute::Proximity;
    UPROPERTY() EVoiceMode      Mode  = EVoiceMode::Normal;
    UPROPERTY() uint8           Loudness = 0;   // RMS 를 0~255 로 양자화
    UPROPERTY() TArray<uint8>   Opus;           // 40~80바이트. 상한 128
};

/** 서버 → 클라. SpeakerId 와 최종 Route 는 서버가 확정한 값이다. */
USTRUCT()
struct FVoiceFrameOut
{
    GENERATED_BODY()

    UPROPERTY() int32           SpeakerId = 0;  // PlayerState::GetPlayerId()
    UPROPERTY() uint16          Seq = 0;
    UPROPERTY() EVoiceRoute     Route = EVoiceRoute::Proximity;  // 우선순위 적용 후
    UPROPERTY() uint8           Loudness = 0;   // 말하는 UI 표시(아이콘)에 쓴다
    UPROPERTY() TArray<uint8>   Opus;
};
```

**`Loudness` 를 uint8 로 보내는 이유.** float 는 4바이트인데 페이로드가 40바이트라 10%다.
음량은 UI 게이지와 소음 반경 배율에만 쓰이므로 256단계면 넘치게 충분하다.

**Opus 상한 128바이트.** 16kHz/24kbps/20ms 면 정상값이 60바이트 근처다. 넘으면 조작이다.

### `URadioComponent` — 무전기 액터에 붙는 인터페이스

**무전기 아이템 액터에 붙인다** (플레이어가 아니라). `ARadio` 생성자가
`CreateDefaultSubobject` 로 붙인다.

```cpp
/** 전원. Z 키로 토글. 서버가 권위. */
UPROPERTY(ReplicatedUsing = OnRep_Power)
bool bPoweredOn = false;

/** ★ 손에 들려 있는가. 송신 자격을 가른다. 서버가 권위. */
UPROPERTY(Replicated)
bool bInHand = false;

/** 사람이 들을 수 있는 거리 */
UPROPERTY(EditAnywhere, BlueprintReadWrite, Category = "Radio|Sound")
float SpeakerHearRadius = 1000.f;

/** ★ NPC 가 들을 수 있는 거리. 밸런스의 주 손잡이 */
UPROPERTY(EditAnywhere, BlueprintReadWrite, Category = "Radio|Sound")
float SpeakerNoiseRadius = 1200.f;

UPROPERTY(EditAnywhere, BlueprintReadWrite, Category = "Radio|Sound")
float SpeakerVolume = 1.0f;

/** 인벤토리에 있을 때 위 두 반경에 곱하는 배율 */
UPROPERTY(EditAnywhere, BlueprintReadWrite, Category = "Radio|Sound")
float StowedRadiusScale = 0.5f;

// --- 서버 전용 -------------------------------------------------
/** 전원을 바꾸고 VoiceRouter 레지스트리에 등록/해제한다. */
void SetPowered(bool bOn);

/** 손에 들었는지 알려준다. ARadio 의 OnEquipped/OnUnequipped 가 부른다. */
void SetInHand(bool bNowInHand);

// --- 조회 (양쪽) -----------------------------------------------
/** 이 무전기를 지금 가지고 있는 사람. **없으면 바닥에 떨어진 것.** */
APlayerState* GetHolder() const;

/** ★ 라우터와 재생 경로는 반드시 이쪽을 쓴다 (아래 ★★) */
float GetEffectiveHearRadius() const;
float GetEffectiveNoiseRadius() const;
```

> **★★ 반경을 직접 읽으면 안 된다.** `SpeakerHearRadius` / `SpeakerNoiseRadius`
> 를 라우터나 재생 경로에서 그대로 쓰면 **인벤토리 감쇠가 적용되지 않는다.**
> 손에 듦/인벤토리 계산은 `GetEffective*` 안에서만 일어나야, 사람이 듣는 반경 ·
> NPC 가 듣는 반경 · 클라 공간화 감쇠 셋이 서로 어긋나지 않는다.

### `ARadio` — 아이템 파트·캐릭터 파트가 부를 것

```cpp
// --- 캐릭터 입력에서 쓴다 --------------------------------------
/** 이 폰이 가진 무전기(손·인벤토리 둘 다). 부착 관계만 타므로
 *  인벤토리 구조를 몰라도 된다. */
static ARadio* FindCarriedBy(const APawn* Pawn);

void TogglePower();               // Z
void SetPowered(bool bOn);        // 클라에서 불러도 서버로 위임된다

void StartTransmit();             // X 누름  (로컬 클라 전용)
void StopTransmit();              // X 뗌    (로컬 클라 전용)

// --- UI 에서 쓴다 ----------------------------------------------
bool  IsPoweredOn() const;
bool  IsInHand() const;
float GetBatteryPercent() const;  // 0~1
bool  HasBattery() const;

// --- 배터리 아이템 등에서 쓴다 (서버 전용) ----------------------
void RechargeBattery(float Amount);
```

**`FindCarriedBy` 를 쓰는 이유**: `Z`/`X` 는 전역키라 "내가 가진 무전기" 를
찾아야 하는데, 특히 `Z` 는 **가방 안의 무전기도 끌 수 있어야 한다.**
`CarryingComponent`(손에 든 것만 안다)로는 부족하다. 이 함수는 부착 관계를
재귀로 훑으므로 손에 든 것도 인벤토리에 넣은 것도 찾는다 — 아이템 파트의
인벤토리 구현이 바뀌어도 깨지지 않는다.

**등록/해제는 반드시 `URadioComponent` 가 `UVoiceRouter` 에 통지한다.**
라우터가 매 프레임 월드의 모든 액터를 훑으면 안 된다 — 무전 프레임마다 O(N) 이 된다.
레지스트리(`TArray<TWeakObjectPtr<URadioComponent>>`)를 유지하면 O(켜진 무전기 수)다.

> **`TWeakObjectPtr` 를 쓰는 이유:** 무전기가 파괴되어도(아이템 소멸) 레지스트리가
> 죽은 포인터를 들고 있지 않게 한다. 순회할 때 `IsValid()` 로 걸러내고 정리한다.

## 11. 스레드 경계

기존 문서 10절의 표와 같은 형식으로 정리한다. **규칙 위반 시 증상까지 적어둔다.**

| 하는 곳 | 해도 되는 것 | 하면 안 되는 것 | 어기면 |
|---|---|---|---|
| `FVoiceCaptureSource` (★게임 스레드 - 아래 이유) | `IVoiceCapture` 폴링, 바이트 배열, RMS/VAD | — | — |
| `UVoiceSubsystem::Tick` (게임) | 캡처 폴링, 재생 버퍼 push, RPC 호출, UI 갱신 | — | |
| `UVoiceRouter` (서버 게임 스레드) | 라우팅, 소음 이벤트, 레지스트리 | 블로킹 I/O | 호스트 프레임 드랍 |
| `UVoicePlaybackComponent` (게임) | 디코딩, 지터버퍼, 링버퍼에 **push** | 링버퍼에서 **pop**, `SetCapacity()` | **use-after-free** (아래 ★) |
| `UVoiceSynthComponent::OnGenerateAudio` (**오디오 렌더**) | 링버퍼에서 **pop**, float 산술 | **UObject / 락 / 메모리 할당 / UE_LOG** | 오디오 끊김 → 크래시 |

> **★ 캡처가 워커 스레드가 아니라 게임 스레드인 이유는 6절 표 아래 각주를 볼 것.**
> 이 시스템의 스레드 경계는 딱 하나뿐이다: **게임 스레드 → 오디오 렌더 스레드**
> (재생 링버퍼). 캡처 쪽은 스레드 경계가 아니다.

> **★ 게임 스레드는 링버퍼를 "비울" 수도 없다.**
> 비우기는 결국 pop 이고, `TCircularAudioBuffer::SetCapacity()` 는 내부 `TArray` 를
> **재할당**한다(`Reset()` + `AddZeroed()`). 렌더 스레드가 그 메모리를 읽는 중이면
> 해제된 메모리를 읽는다. **실제로 이 버그를 냈다가 리뷰에서 잡았다**(14-1절).
>
> 올바른 방법: 게임 스레드는 `RequestFlush()` 로 **요청만** 하고,
> 실제 비우기는 렌더 스레드가 `OnGenerateAudio` 안에서 `Pop()` 으로 한다.

**큐는 전부 SPSC 다.** 채팅과 같다. 각 큐를 반대편에서 쓰면 안 된다.

**종료 순서** (기존 `ShutdownClient` 와 같은 이유로 순서가 중요하다):

1. `Capture->Stop()` — 마이크 정지
2. `Runnable->Stop()` → `Thread->Kill(/*bShouldWait=*/**true**)` → `delete Runnable`
3. `SynthComponent->Stop()` 후에 링버퍼 해제 — **순서를 뒤집으면 오디오 렌더 스레드가 해제된 버퍼를 읽는다**

`bShouldWait=false` 로 두면 **PIE 를 껐다 켤 때 에디터가 죽는다.** 채팅에서 이미 겪은 문제다.

## 12. 대역폭 계산

가정: 16kHz mono, Opus 24kbps, 20ms 프레임 → 페이로드 60바이트 + UE 오버헤드 ~40바이트
= **100바이트/프레임**, 초당 50프레임 = **5 KB/s (스트림 1개)**

**8인 플레이, 반이중 + 근접 거리 컷 적용 (현실값)**

```
무전 동시 송신 = 1명 (반이중 강제)  → 최대 7명이 수신
근접 동시 발화 = 실측 2~3명, 각자 평균 3명이 들음
  (라우트 우선순위 덕분에 한 수신자가 중복으로 받지 않는다)

1 × 7 + 3 × 3 = 16 스트림 → 호스트 업로드 80 KB/s = 640 kbps
클라이언트 수신 = 동시 3~4 스트림 → 20 KB/s
```

**LAN 시연(이 프로젝트의 확정 환경)에서는 여유롭다.**
인터넷으로 확장한다면 40ms 프레임(패킷 절반) + Opus 16kbps 로 내리면 절반이 된다.

**반이중이 없으면** 8명 전원 송신 시 8×7 = 56 스트림 = 280 KB/s 로 뛴다. 이래서 넣는다.

**측정 방법.** `Stat Net` 과 `MOU.Voice.Stat`(초당 프레임 수 / 스트림 수 / 드랍 수).
**추측하지 말고 숫자를 본다** — 기존 문서가 프레이밍 회귀 테스트를 둔 것과 같은 이유다.

## 13. 튜닝 파라미터

무전기 관련 반경은 **`URadioComponent` 에 `EditAnywhere`** 로 두어 아이템별로 조절한다.
나머지 전역 값은 `UDeveloperSettings`(`UVoiceSettings`)로 빼서 `DefaultGame.ini` 에서 만진다.
코드 재컴파일 없이 밸런싱하기 위해서다.

**오디오**

| 이름 | 기본값 | 설명 |
|---|---|---|
| `SampleRate` | 16000 | 바꾸면 인코더/디코더 양쪽. **8000·12000·16000·24000·48000 만 허용** |
| `FrameMs` | 20 | **★ 아래 주의** — 40 으로 올리면 대역폭이 줄긴 하지만 이유가 다르다 |
| `OpusBitrate` | 24000 | 프레임당 바이트를 결정. 12절 대역폭 계산의 근거 |
| `TargetJitterFrames` | 3 (60ms) | 낮추면 반응 빠름 / 끊김 증가 |
| `MaxJitterFrames` | 8 | 넘으면 오래된 것부터 버림 |
| `VadThreshold` | 0.02 | **옵션 화면에서 사용자가 조절** (9절) |
| `VadHangoverMs` | 200 | 말끝이 잘리지 않게 |

> **★ `FrameMs` 는 사실상 20 에 고정이다 (V2 에서 확인).**
> 엔진 Opus 래퍼가 `FrameSize = SampleRate / 50` 로 하드코딩돼 있어 **320샘플
> 단위로만** 인코딩한다. 40 으로 바꾸면 "40ms 프레임" 이 되는 게 아니라
> **"한 패킷에 20ms 프레임 2개"** 가 되고, 대역폭이 주는 이유는 **헤더 공유**다.
> **320 의 배수가 아닌 값으로 바꾸면 나머지가 조용히 버려진다.** 자세한 것은 14-4절.

**발화 모드 — 밸런스의 핵심**

| 모드 | **총 가청 거리**<br>(= Radius + Falloff) | 내역<br>Radius / Falloff | 소음 `MaxRange` | Loudness 배율 |
|---|---|---|---|---|
| 속삭임 | 500 (5m) | 150 / 350 | 700 | 0.35 |
| 보통 | 1500 (15m) | 300 / 1200 | 1800 | 1.0 |
| 외침 | 3000 (30m) | 500 / 2500 | 4000 | 1.6 |

> **"총 가청 거리" 는 `Radius + FalloffDistance` 의 합이다.** 언리얼 감쇠 에셋에
> 이 숫자를 그대로 넣으면 안 된다 — 분해해서 넣어야 한다. 자세한 것은 7-2절.

> **소음 반경이 들리는 반경보다 넓다.** 의도된 것이다(7-4절과 같은 이유).

**무전**

| 이름 | 기본값 | 어디서 | 설명 |
|---|---|---|---|
| `SpeakerHearRadius` | 1000 | **컴포넌트** | 사람이 듣는 거리 |
| `SpeakerNoiseRadius` | 1200 | **컴포넌트** | **NPC 가 듣는 거리 ★** |
| `SpeakerVolume` | 1.0 | **컴포넌트** | 출력 음량 |
| `RadioChannelHoldMs` | 300 | 전역 | 반이중 점유 해제 시간 |
| `RadioMouthNoiseScale` | 0.35 | 전역 | 무전 송신 시 발화자 육성 소음 배율 |

**AI**

| 이름 | 기본값 | 설명 |
|---|---|---|
| `NoiseWindowSec` | 0.3 | 소음 보고 집계 창. 낮추면 서버 부하 증가 |
| `MaxFramesPerSecPerPlayer` | 60 | 레이트 리밋 |

**1번이 가장 급하다.** `URadioComponent::GetHolder()` 는 부착 관계로 주인을
판정하는데, 현재 `AItemBase::PickUp_Implementation` 은 물리만 끄고 **attach 를
하지 않는다**("추후 MainCharacter 및 Component 에서 호출 처리 연동" 주석 상태).
인벤토리에 넣을 때(`OnUnequipped`)만 attach 된다. 그래서 지금은 **손에 든
무전기가 주인 없는 것으로 판정된다.**

> 그때까지의 검증 수단은 `AVoiceDebugRadio` 다 — 스스로 attach 하므로 무전
> 파이프라인 자체는 지금도 콘솔로 확인할 수 있다.

**3번 입력 바인딩은 이렇게 붙인다** (`AMainCharacter::SetupPlayerInputComponent`):

```cpp
// Z: 전원 토글
EnhancedInputComponent->BindAction(RadioPowerAction, ETriggerEvent::Started,
    this, &AMainCharacter::OnRadioPower);

// X: PTT — Started/Completed/Canceled 셋 다 붙인다
EnhancedInputComponent->BindAction(RadioTalkAction, ETriggerEvent::Started,
    this, &AMainCharacter::OnRadioTalkStart);
EnhancedInputComponent->BindAction(RadioTalkAction, ETriggerEvent::Completed,
    this, &AMainCharacter::OnRadioTalkEnd);
EnhancedInputComponent->BindAction(RadioTalkAction, ETriggerEvent::Canceled,
    this, &AMainCharacter::OnRadioTalkEnd);
```

> **★ `Canceled` 를 빼면 안 된다.** 키를 누른 채 창 포커스를 잃으면 `Completed`
> 가 오지 않는다 — **송신이 안 끊긴 채로 남아 계속 떠들게 된다.**

핸들러는 `ARadio::FindCarriedBy(this)` 로 무전기를 찾아 `TogglePower()` /
`StartTransmit()` / `StopTransmit()` 을 부르면 끝이다.

### 14-2. 캡처를 워커 스레드 → 게임 스레드로 되돌림 (2026-08-13, 실사용 중 발견)

**실제로 PIE 에서 루프백을 들어보니 "마이크가 준비되지 않았다" 는 문제가 났다.**
원인을 추적하면서 설계를 하나 뒤집었다.

**증상의 직접 원인**: `FVoiceCaptureRunnable::Init()` 에서
`FVoiceModule::IsAvailable() || FVoiceModule::Get().IsVoiceEnabled()` 순서로 검사했는데,
`IsAvailable()` 은 `IsModuleLoaded("Voice")` 라서 **아무도 모듈을 로드한 적이 없으면
false** 다. `||` 단락 평가로 실제 로드를 수행하는 `Get()` 에 영원히 도달하지 못했다.
Build.cs 의존성은 **링크**만 보장하고 런타임 로드는 별개라는 걸 놓쳤다.

**원인을 파다가 더 심각한 걸 발견했다**: 엔진 Windows 캡처 구현을 열어보니

```cpp
class FVoiceCaptureWindows : public IVoiceCapture, public FTSTickerObjectBase
```

**엔진의 캡처 객체는 게임 스레드 티커로 자기 내부 버퍼를 채우고, 그 버퍼에
뮤텍스가 없다.** 워커 스레드에서 `GetVoiceData()` 를 폴링한 애초의 설계(6절 옛 표,
11절 옛 표) 자체가 **데이터 레이스**였다. 기존 채팅(`FServerClientRunnable`)의 패턴을
그대로 따라간 게 여기서는 틀렸다 — 채팅은 우리가 소켓을 직접 다루니 워커가 맞지만,
음성 캡처는 엔진이 이미 게임 스레드에 묶어놓은 리소스다.

**조치**: `FVoiceCaptureRunnable`(워커) 를 폐기하고 `FVoiceCaptureSource`(순수
클래스, 게임 스레드 전용)로 교체했다. `UVoiceSubsystem::Initialize()` 에서
`FModuleManager::Get().LoadModule(TEXT("Voice"))` 를 명시적으로 호출해 모듈을
로드한 뒤 캡처를 연다. 구조가 오히려 단순해졌다 — 큐도, 원자적 타입도 필요 없다.
**진짜 스레드 경계는 재생 쪽 하나뿐**이라는 게 이번에 명확해졌다.

**진단 명령 추가**: `MOU.Voice.Diag` — "마이크가 준비되지 않았다" 는 증상의 원인이

> 여러 사람의 목소리를 디코더 하나로 돌려 쓰면 서로의 상태를 오염시켜 지직거린다.
> V3 에서 `UVoicePlaybackComponent` 가 `(발신자, 라우트)` 쌍마다 하나씩 들게 된다.

**★★ 엔진 코드를 읽고서야 알게 된 함정 3가지**

이 셋은 전부 **에러 없이 조용히 무음이 되는** 종류다. 로그도 안 나오므로
모르고 부딪히면 마이크·오디오 장치·볼륨을 의심하며 시간을 날린다.

**1. 20ms 는 우리 선택이 아니라 엔진이 강제하는 값이다**

```cpp
// VoiceCodecOpus.cpp
#define NUM_OPUS_FRAMES_PER_SEC 50
FrameSize = SampleRate / NUM_OPUS_FRAMES_PER_SEC;   // 16000/50 = 320
```

프레임 길이를 인자로 받지 않는다. **무조건 320샘플 단위로만** 인코딩한다.
우리 프레이밍이 마침 같아서 1프레임 = 1 Opus 프레임으로 딱 떨어졌다.

> **13절의 "`FrameMs` 를 40 으로 올리면 대역폭 절반" 은 설명이 틀렸다.**
> 40 으로 바꿔도 "40ms Opus 프레임" 이 되지 않는다. **"한 패킷에 20ms 프레임 2개"**
> 가 된다 — 엔진이 들어온 바이트를 320샘플씩 쪼개 `opus_encode` 를 두 번 부르고
> 헤더 하나에 묶는다. 대역폭이 주는 것은 맞지만 이유는 **헤더 공유**다.
> 그리고 **320 의 배수가 아닌 값으로 바꾸면 나머지가 조용히 버려진다.**

**2. 압축 결과는 순수 Opus 가 아니라 엔진이 정의한 컨테이너다**

```
[0]      프레임 개수 (uint8)
[1]      Generation — 패킷 순번. 디코더가 유실을 감지한다 (uint8)
[2..]    프레임마다 압축 끝 오프셋 (uint16 × 프레임개수)
[그 뒤]  실제 Opus 데이터
```

**다른 Opus 구현으로는 못 푼다.** 반대쪽도 반드시 엔진 디코더여야 한다.
우리는 양쪽 다 UE 라 문제가 없지만, **나중에 외부 클라이언트(모바일 등)를 붙일
계획이 생기면 이 지점이 발목을 잡는다**는 것은 알고 있어야 한다.

**3. ★ 디코딩 출력 버퍼는 6프레임 크기여야 한다 (제일 위험)**

```cpp
// VoiceCodecOpus.cpp, FVoiceDecoderOpus::Decode()
#define MAX_OPUS_FRAMES 6
if (UncompressedBufferAvail >= (MAX_OPUS_FRAMES * BytesPerFrame))  // 6*640 = 3840
{ ...디코딩... }
else
{ UE_LOG(..., "Decompression buffer too small to decode voice"); break; }
```

**남은 공간이 3840바이트 미만이면 디코딩을 통째로 건너뛴다.**

20ms 프레임 하나를 넣었으니 320샘플(640바이트) 버퍼면 되겠다고 생각하는 것이
자연스러운데, **그러면 반환 샘플 수가 0 이고 에러도 아니다.**
"인코딩은 되는데 소리만 안 난다" 로 보인다.

> 그래서 `MOUVoice::DecodeScratchSamples = 6 * SamplesPerFrame`(1920) 로 두고,
> **줄이지 말라는 이유를 상수 주석에 길게 적어두었다.** 나중에 "메모리 낭비 같은데"
> 하고 320 으로 줄이는 최적화가 반드시 시도될 자리다.

**미리 심어둔 안전장치 두 가지**

| 장치 | 막으려는 것 |
|---|---|
| 압축 프레임이 `MaxEncodedFrameBytes`(128) 초과 시 **경고 1회** | V3 의 Unreliable RPC 는 큰 페이로드를 **조용히 버린다**(15절). V3 에서 터지면 "특정 사람 목소리만 안 들린다" 로 나타나 추적이 매우 어렵다. **V2 단계에서 미리 감시한다** |
| 디코딩 실패 시 **원본 PCM 으로 대체하지 않음** | 대체하면 코덱이 완전히 고장나 있어도 소리는 멀쩡히 나서 V3 에 가서야 발견하게 된다. 조용한 편이 낫다 — 실패 횟수는 `MOU.Voice.Stat` 에 남는다 |

**비트레이트를 명시적으로 박은 이유.** 엔진 `Init()` 은 VBR 만 켜고 비트레이트는
Opus 자동값에 맡긴다. 그러면 12절의 "프레임당 ~60바이트" 계산에 근거가 없어진다.
`SetBitrate(24000)` 으로 못박아야 대역폭을 예측할 수 있고, 나중에 인터넷으로
확장할 때 내릴 여지도 생긴다.

**발화가 끝나면 디코더를 리셋한다.** 안 하면 새 발화의 첫 프레임이 **몇 초 전에
끊긴 소리를 참고해서** 복원되어 말 첫머리가 짧게 지직거린다. 리셋 시점은
`bIsSpeaking` 이 hangover 까지 다 돌고 내려간 뒤다 — 프레임 단위로 보면
hangover 로 아직 살아있는 구간을 발화 종료로 오판한다. 음소거(`C`)는 Tick 의
발화 종료 감지를 우회하므로 `SetMuted()` 안에서 따로 리셋한다.

**아직 확인하지 못한 것**

- **★ 압축을 통과한 소리를 귀로 듣기.** `MOU.Voice.Loopback 1` 을 켜고
  `MOU.Voice.Codec` 을 0/1 로 왕복하며 같은 말을 반복해 비교한다.
  **"전화 수준이면 합격" 은 숫자로 판정할 수 없다 — 반드시 귀로 확인해야 한다.**

- 코덱 삽입으로 지연이 늘었는지. 역시 `MOU.Voice.Stat` 의 `재생버퍼=...ms`.

> 값"(512바이트)만 걸러 끊고, 규격 위반(128 초과)은 라우터가 조용히 버린다.
> 정상 상한으로 여기서 끊으면 **비트레이트 설정이 조금 어긋난 팀원이 게임에서 튕긴다.**

> **★ 리슨서버 호스트는 RPC 를 "타지 않는다" (15절).**
> 호스트는 서버이자 클라라 언리얼이 RPC 를 네트워크로 보내지 않고 **그 자리에서
> 함수를 부른다.** 결과적으로 코드는 똑같이 동작하므로, `VoiceComponent.cpp` 에

> 그런 분기를 넣으면 "호스트만 아무 소리도 안 들린다" 가 된다.

**감쇠 숫자가 어긋나지 못하게 컴파일 타임에 못박았다**

7-2절의 `Radius + FalloffDistance = 총 가청 거리` 관계를 `VoiceTypes.h` 에서
`static_assert` 로 검사한다. 세 숫자 중 하나만 고치면 **빌드가 깨진다.**

> 어긋나면 증상이 고약하다: 서버는 `GetHearRadius` 로 전송을 끊는데 클라 감쇠는
> 다른 거리에서 0 이 되므로, **경계에서 목소리가 뚝 끊기거나**(감쇠가 더 길 때)
> **들려야 할 거리인데 소리가 없다**(감쇠가 더 짧을 때). 둘 다 "가끔 이상하다"
> 로만 보여서 원인을 찾기 매우 어렵다.

**아직 확인하지 못한 것 — ★ 전부 실행 검증이다**

빌드만 통과했고 **에디터에서 한 번도 돌려보지 않았다.**

- **PIE 2창에서 실제로 들리는지.** 창 하나가 말하고 다른 창이 듣는다.
  (마이크는 첫 창만 잡는다 — 양방향은 프로세스 두 개로)
- **거리에 따라 사라지는지.** `MOU.Voice.ShowRadius 1` 로 초록 링을 띄우고
  링 안팎을 오가며 확인한다. **경계에서 뚝 끊기면 `FalloffMode` 정렬이 틀린 것이다.**
- **소리가 발신자 위치에서 나는지**(방향감). 안 되면 `SetProximityMode` 가
  `Start()` 뒤에 불렸을 가능성이 높다.
- **호스트도 들리는지.** 위 리슨서버 항목이 실제로 맞는지는 돌려봐야 안다.
- `MOU.Voice.Stat` 의 `전송 / [서버]라우팅·전달 / [수신]재생` 이 어디서 0 이 되는지.
  **이 세 숫자로 송신·서버·수신 중 어디가 문제인지 바로 갈린다** — 안 들릴 때 여기부터 본다.

### 14-6. V4 구현 결과 — 지터버퍼와 유실 은폐 (2026-08-18)

**만든 파일**

| 파일 | 역할 |
|---|---|
| `Public/Voice/VoiceJitterBuffer.h`<br>`Private/Voice/VoiceJitterBuffer.cpp` | 프레임을 번호 순서로 다시 세운다. 순수 로직(UObject 아님) |

**이 단계에서 바뀐 것 한 줄: 도착과 재생을 분리했다**

```
V3:  ClientReceiveVoiceFrame ──▶ 디코딩 ──▶ 재생   (도착한 박자 그대로 재생)
V4:  ClientReceiveVoiceFrame ──▶ 지터버퍼에 넣기
     매 틱 PumpStream        ──▶ 꺼내기 ──▶ 디코딩 ──▶ 재생   (일정한 박자로)
```

UDP 는 20ms 마다 보내도 5ms·40ms·3ms 로 도착하고 순서도 뒤집힌다.
그 박자대로 재생하면 **흔들림이 그대로 소리의 끊김이 된다.** 몇 프레임을
모아두고 그 뒤에서 꺼내 쓰면 늦게 온 프레임도 제자리를 찾는다 —
**지연(60ms)을 주고 안정성을 사는 것**이 지터버퍼의 전부다.

> **★ 재생 박자를 우리가 재지 않는다.** 오디오 스레드가 링버퍼를 실시간 속도로
> 비우므로, 게임 스레드는 "덜 찼으면 채운다" 만 하면 20ms 간격이 저절로 맞는다.
> 게임 틱(가변)으로 직접 박자를 맞추려 하면 오디오 주기(고정)와 어긋나 조금씩
> 밀리거나 쌓인다.

**설계 대비 달라진 것**

| 설계 문서 | 실제 구현 | 이유 |
|---|---|---|
| 지터버퍼를 `UVoicePlaybackComponent` 안에 (6절) | **별도 클래스로 분리** | 순환 산술과 유실 판정은 혼자 틀리기 쉬운 로직이다. 떼어내면 눈으로 검증할 수 있다 |
| PLC | **직접 구현**(직전 프레임 감쇠 반복) | ★ 아래 |
| 컴포넌트 틱 0.5초 (V3) | **매 프레임** | 링버퍼가 비어가는 것을 보고 채우는 구조라 틱이 느리면 그만큼 소리가 끊긴다 |

**★★ 엔진 Opus 래퍼로는 진짜 PLC 를 쓸 수 없다**

Opus 자체는 `opus_decode(dec, NULL, 0, ...)` 로 유실 구간을 그럴듯하게 합성해준다.
그런데 엔진 래퍼가 그 경로를 막아놨다:

```cpp
// VoiceCodecOpus.cpp, FVoiceDecoderOpus::Decode()
if (!InCompressedData || (CompressedDataSize < HeaderSize))
{ OutRawDataSize = 0; return; }   // <- null 을 넘기면 그냥 0샘플
```

`IVoiceDecoder` 인터페이스에 "이번 프레임은 유실됐다" 를 알릴 방법이 아예 없다.
그래서 **PCM 단계에서 직접 메운다** — 직전 프레임을 감쇠시켜 반복하고(0.5배씩),
3프레임(60ms)을 넘으면 무음으로 전환한다.

> 왜 무한정 반복하지 않는가: 같은 소리를 계속 반복하면 사람 목소리가 아니라
> **기계음처럼 웅웅거린다.** 짧게 덮을 때만 도움이 되고, 길어지면 조용한 편이 낫다.

**★ 유실과 "아직 안 옴" 을 구분하는 것이 이 버퍼의 핵심이다**

| 상황 | 판단 근거 | 조치 |
|---|---|---|
| 기다리는 번호가 없는데 **뒤 번호는 도착해 있다** | 순서가 뒤집힌 게 아니라 진짜 안 온 것 | 유실 확정 → 은폐 |
| 기다리는 번호가 없고 **버퍼가 통째로 비었다** | 그냥 아직 안 왔을 뿐 | 기다린다 |

> 둘을 구분하지 않고 전부 은폐하면, **네트워크가 멀쩡한데도 소리가 지직거린다** —
> 멀쩡히 오고 있는 프레임을 은폐 프레임이 계속 밀어내기 때문이다.

**★ Seq 순환(22분마다 65535 → 0)은 전부 uint16 차이 계산으로 견딘다**

`if (A > B)` 같은 크기 비교를 쓰면 순환하는 순간 "6만 개를 잃었다" 가 되어
스트림이 통째로 무너진다. **22분에 한 번, 재현도 안 되는 버그**가 된다.
`VoiceJitterBuffer.cpp` 의 모든 순서 판정은 차이를 uint16 으로 계산한다.

**튜닝 손잡이**

| 이름 | 기본값 | 뜻 |
|---|---|---|
| `TargetJitterFrames` | 3 (60ms) | **이 값이 곧 추가 지연이다.** 낮추면 반응이 빠르고 잘 끊긴다 |
| `MaxJitterFrames` | 8 | 재정렬 가능 범위. 넘으면 따라잡기(재동기화) |
| `MaxConcealFrames` | 3 | 이보다 길게 끊기면 은폐 대신 무음 |
| `ConcealFadePerFrame` | 0.5 | 은폐 프레임마다 곱하는 감쇠 |

**아직 확인하지 못한 것**

- **빌드조차 안 됐다** (에디터가 열려 있어 Live Coding 이 막았다).
- 설계 문서의 V4 합격 기준: 콘솔에서 `Net PktLoss=10` 을 넣고도 알아들을 수 있는지.
- `MOU.Voice.Stat` 의 `지터깊이` 가 목표(60ms) 근처에서 안정적인지.
  **계속 오르면** 재동기화가 반복되는 것이고, **0 근처에서 끊김이 오르면**
  목표 깊이가 너무 낮은 것이다.

코드가 경우를 나눌 필요가 없다.

> **★ (2026-08-20 결정) 폐기된 부분**: 원래는 "바닥에 떨어져도 켜진 채로 계속
> 소리를 내 시체 주변을 위험지대로 만든다" 였다. **폐기됐다** — 대신 떨어지면
> 자동으로 꺼지고, 주인 없는 무전기는 애초에 소리를 내지 않는다. 자세한 내용은
> 아래와 7-4절.

**★ 손에 듦과 인벤토리는 코드에서 별도 상태다**

부착 관계(`GetAttachParentActor`)만으로는 "손에 들었다" 와 "인벤토리에 넣었다"
를 구분할 수 없다 — 인벤토리에 넣어도 아이템 액터는 플레이어에 부착된 채로
남는다("투명한 주머니"). 그래서 `URadioComponent` 에 `bInHand`(서버 권위, 복제)
를 별도로 두고, 아이템 쪽(`ARadio::OnEquipped_Implementation` /
`OnUnequipped_Implementation`)이 `SetInHand()` 로 알려준다.

`bInHand` 는 **송신 자격을 가른다**(`UVoiceRouter::FindUsableRadioFor` 가 확인)
— 인벤토리에 있으면 수신만 되고 무전을 칠 수는 없다. 반경 감쇠(`StowedRadiusScale`)
에도 쓰인다.

**★ 드롭/던지기 = 전원 자동 OFF**

`ARadio::Drop_Implementation` / `Throw_Implementation` 이 소유권 해제와 같이
전원을 끈다. 자발적 드롭(G 키)과 사망·기절로 인한 낙하를 구분하지 않는다 —
어느 경로든 무조건 꺼진다. 라우터도 `GetHolder()` 가 null 인 무전기는 재생·소음
발행을 건너뛰므로(7-4절), 사망 처리가 `Drop()` 을 거치지 않고 단순히 부착만
풀어도 안전하다.

**★ 무전 라우팅이 근접과 근본적으로 다른 점**

```
근접:  발신자 주변 사람에게   → 소리는 **발신자 폰**에서 난다
무전:  켜진 무전기마다 그 주변 사람에게 → 소리는 **듣는 쪽 근처의 무전기**에서 난다
```

"무전을 켠 사람에게 보낸다" 가 아니라 **"켜진 무전기에서 소리가 나고, 그 소리가
닿는 사람이 듣는다"** 이다. 그래서 무전기 주인만이 아니라 **주변 사람도 듣고,
V8 에서는 NPC 도 듣는다**(7-4절). 단, **주인이 없는 무전기는 이 라우팅 대상에서
아예 제외된다** — 켜진 채로 바닥에 떨어져도(이론상 `Drop()` 을 거치지 않은
예외 경로라면) 조용하다.

**★ 소지 개수 제한은 라우터가 보장한다**

두 대를 들고 있어도 `RouteRadio` 가 홀더당 한 대만 재생한다(`HandledHolders`).
아이템 파트가 소지 개수를 막지 않아도 소리가 겹치는 일은 없다.

**★ 배터리는 새 변수가 아니라 기존 내구도를 재사용한다**

`AItemBase::CurrentDurability` (이미 복제, `OnRep_CurrentDurability` 훅 보유)
를 그대로 쓴다. 켜져 있는 동안(손에 들었든 인벤토리든) 서버 타이머가 초당
`BatteryDrainPerSecond` 만큼 깎고, 0 이 되면 스스로 꺼진다. "켜둔 채로 인벤토리에
넣어도 배터리는 닳는다" 가 핵심 — 그래야 켜 둘지 말지가 매번 실제 선택이 된다.

**★ 라우트 우선순위(근접 > 무전)를 어떻게 구현했나**

근접을 먼저 돌리며 보낸 사람을 `TSet` 에 기록하고, 무전 패스에서 그 사람들을
건너뛴다. 무전을 치는 동안에도 **육성은 그대로 나가므로**(2절) 가까이 있는
사람은 두 조건에 다 걸리는데, 둘 다 보내면 같은 목소리가 겹쳐 **에코가 된다.**

**전원 OFF = 기기 종료** (음소거가 아니다)

`SetPowered(false)` 는 볼륨을 0 으로 만드는 것이 아니라 **라우터 레지스트리에서
자기를 제거한다.** 그 순간부터 프레임이 아예 안 간다 — 개조 클라이언트가
"꺼진 척하며 다 듣는" 것을 원천 차단한다(7-3절).

**반이중**: 서버가 한 명만 점유하게 하고 0.3초간 프레임이 없으면 푼다.
진짜 이유는 무전기다움이 아니라 **대역폭 상한**이다(12절).

#### V7 — 무전 톤

**★ 설계와 달라진 점: 에셋이 아니라 코드로 넣었다**

7-4절은 `USoundEffectSourcePresetChain` 에셋을 쓰라고 했고 그 이유(디자이너가

없는 동안 무전이 맑은 목소리로 들리면 "무전기 같은가" 를 판단할 수가 없다.

그래서 `OnGenerateAudio` 안에 기본 톤을 넣었다. 나중에 에셋이 생기면
`USynthComponent::SourceEffectChain`(엔진이 이미 갖고 있다)에 지정하고

### 14-8. V9 구현 결과 — 무전기가 진짜 아이템이 되다 (2026-08-20)

**만든 파일**: `Public/Voice/Radio.h`, `Private/Voice/Radio.cpp`
**고친 파일**: `RadioComponent`, `VoiceRouter`, `VoicePlaybackComponent`, `VoiceDebugRadio`
**건드리지 않은 파일**: `Base/ItemBase.*` (다른 파트 소유)

#### ★ 설계에서 폐기된 것 — "떨어진 무전기가 NPC 를 유인한다"

원안의 재미 포인트 하나가 **폐기됐다.** NPC 를 끌어들이는 것은 무전기가 아니라
**그것을 들고 있는 사람**이어야 한다는 방향으로 정리됐다. 그래서:

- 드롭/던지기 → **전원 자동 OFF** (자발적/비자발적 구분 없음)
- 주인(`GetHolder()`)이 없는 무전기 → 라우터가 재생·소음 발행을 **건너뛴다**

두 겹을 다 둔 이유는, 사망 처리가 `Drop()` 을 거치지 않고 부착만 풀 수도 있기
때문이다. 그 경우에도 소리는 나지 않는다.

> **컴포넌트를 아이템에 붙인 결정 자체는 그대로 유효하다.** 근거가 "떨어져도
> 소리가 난다" 에서 "**소리 위치를 액터 하나로 통일한다**" 로 바뀌었을 뿐이다.

#### ★ 부착 관계만으로는 손/인벤토리를 구분할 수 없었다

가장 손이 많이 간 부분이다. `GetHolder()` 는 부착을 타고 올라가 주인을 찾는데,
`AItemBase::OnUnequipped` 가 **인벤토리에 넣을 때도 플레이어에 attach 한다**
("투명한 주머니"). 그래서 손에 든 것과 가방에 넣은 것이 코드에서 완전히 같다.

`ItemBase` 를 고칠 수 없으므로 `URadioComponent` 에 `bInHand`(복제)를 두고
`ARadio` 의 `OnEquipped`/`OnUnequipped` 가 알려주게 했다. 이 값이:

- `FindUsableRadioFor` 의 **송신 자격**을 가르고
- `GetEffective*Radius()` 의 **인벤토리 감쇠**를 가른다

> **컴포넌트가 `AItemBase` 를 모른다는 원칙은 유지됐다.** bool 하나를 받을 뿐이라
> 여전히 어떤 액터에 붙여도 동작한다.

#### ★ 클라 감쇠가 상수를 쓰고 있었다 (숨어 있던 버그)

`VoicePlaybackComponent` 가 `MOUVoice::DefaultSpeakerHearRadius` **상수**로
공간화를 설정하고 있었다. 무전기별 반경을 읽지 않았다는 뜻이다. 그대로 뒀다면
인벤토리 감쇠를 넣어도 **"닿는 사람은 줄었는데 들리는 크기는 똑같은"** 상태가
됐을 것이다. 이제 `Stream.RadioActor` 에서 `URadioComponent` 를 찾아
`GetEffectiveHearRadius()` 를 쓴다.

> 공간화 설정은 synth 생성 시점에 한 번만 읽힌다. 송신 도중에 무전기를 집어넣으면
> 그 스트림은 옛 반경으로 끝난다 — 한 번의 송신 안에서 일어나는 일이라 무시할 만하다.

#### ★ 소지 개수 제한을 아이템 파트에 맡기지 않았다

`RouteRadio` 가 `HandledHolders` 셋으로 **홀더당 한 대만** 재생한다. 원래는
"소지 개수 제한은 아이템 파트 몫" 이었는데, **인벤토리에서도 수신되게 하면서
두 대를 갖기가 훨씬 쉬워졌다.** 라우터에서 막는 편이 안전하다.

#### 배터리 — 새 변수를 만들지 않았다

`AItemBase::CurrentDurability` 를 그대로 쓴다(6-1절). 서버 타이머 1초 간격,
켜져 있는 동안만 닳고 0 이 되면 스스로 꺼진다. **인벤토리에 있어도 닳는다** —
그래야 "켜둔 채로 넣어둘까" 가 매번 실제 선택이 된다.

#### 아직 확인하지 못한 것

- **빌드까지만 했다.** PIE 실행 검증은 못 했다 — **장착 시 attach 가 아직 없어서
  구조적으로 불가능하다**(14절 "지금 바로 다음에 할 일" 1번).
- `Z`/`X` 입력 바인딩이 아직 없다. 지금은 콘솔 명령으로만 조작된다.
- `ARadio` 기반 BP 와 메시가 없다.

- `SynthComponent` 를 매 발화마다 `NewObject` 하면 GC 압력이 생긴다. **스트림 풀을 만들어 재사용한다.**

**코덱 (V2 에서 실제로 부딪힌 것들 — 자세한 것은 14-4절)**

- **★ 디코딩 출력 버퍼가 6프레임(3840바이트)보다 작으면 조용히 0샘플이 나온다.**
  에러도 로그도 없다. "인코딩은 되는데 소리만 안 난다" 로 보인다.
  `MOUVoice::DecodeScratchSamples` 를 **줄이는 최적화를 하면 안 된다.**
- **프레임 길이는 20ms 고정이다.** 엔진이 `SampleRate / 50` 로 하드코딩했다.
  320샘플의 배수가 아닌 입력은 나머지가 조용히 버려진다.
- **압축 결과는 순수 Opus 가 아니다.** 엔진 정의 컨테이너라 다른 Opus 구현으로 못 푼다.
- **Opus 디코더는 상태를 가진다.** 발신자마다 하나씩 둘 것. 하나를 돌려 쓰면 지직거린다.
  발화가 끊기면 `Reset()` 을 부를 것. 안 하면 새 발화 첫머리가 지직거린다.

**네트워크**

- Unreliable RPC 는 **한 패킷에 들어가야 한다.** 페이로드가 커지면 조용히 버려진다. 128바이트 상한은 이 때문이기도 하다.
  **V2 에 감시를 심어뒀다** — 압축 프레임이 128바이트를 넘으면 경고가 한 번 뜬다(14-4절).
- 폰이 relevant 하지 않으면 그 폰의 RPC 는 안 간다. **그래서 `PlayerController` 에 컴포넌트를 둔다.**(6절)
- **리슨서버의 호스트 본인은 RPC 를 타지 않는다.** 서버=클라 동일 프로세스이므로 라우팅 결과를
  직접 재생 경로에 넣어야 한다. 빼먹으면 "호스트만 아무 소리도 안 들린다" 가 나온다. **자주 나는 버그다.**

**무전기 / 아이템**

- **★ 전원 OFF 를 클라이언트 음소거로 구현하면 안 된다.** "볼륨 0" 이나 "재생 건너뛰기" 로
  만들면 서버는 계속 프레임을 보내고 있어서 **개조 클라이언트가 꺼진 척하며 다 들을 수 있다.**
  반드시 **서버 레지스트리에서 제거**해서 프레임 자체가 가지 않게 한다(7-3절).
- **무전기가 파괴되면 레지스트리에 죽은 포인터가 남는다.** `TWeakObjectPtr` + `IsValid()` 필수.
- **전원 상태 규칙은 V9 에서 확정됐다**: 드롭/던지기 = **OFF**, 인벤토리 = **유지**.
  줍는 것만으로는 켜지지 않는다 — 켜는 것은 언제나 `Z` 로 하는 직접 조작이다.
- 무전기를 **두 개 이상 가지면** 소리가 두 번 난다. **V9 에서 라우터가 막았다**
  (`RouteRadio` 의 `HandledHolders`, 홀더당 1대). 아이템 파트가 소지 개수를
  제한하지 않아도 겹치지 않는다.
- **★ 반경을 `SpeakerHearRadius` 로 직접 읽으면 인벤토리 감쇠가 빠진다.**
  반드시 `GetEffectiveHearRadius()` / `GetEffectiveNoiseRadius()` 를 쓴다(10절 ★★).
  실제로 `VoicePlaybackComponent` 가 상수를 쓰고 있어서 V9 에서 고쳤다.
- **★ `OnEquipped`/`OnUnequipped` 는 멀티캐스트로 모든 클라에서 불린다.**
  거기서 `StopTransmit()` 같은 **로컬 조작을 조건 없이 하면 남이 무전기를
  집어넣었는데 내 송신이 끊긴다.** `ARadio::IsLocalPlayerActor` 로 걸러야 한다.
- **★ 손에 든 것과 인벤토리에 넣은 것은 부착 관계로 구분되지 않는다.**
  `AItemBase::OnUnequipped` 가 인벤토리에 넣을 때도 플레이어에 attach 하기
  때문이다. `URadioComponent::IsInHand()` 를 봐야 한다(14-8절).

**PIE / 장치**

- PIE 다중 창에서 마이크 장치 경합 → 첫 창만 캡처(6절).
- 마이크가 없거나 권한이 없으면 `CreateVoiceCapture` 가 null 을 준다.
  **전체 시스템이 죽지 않고 재생만 동작해야 한다.**
- Windows 마이크 권한을 끈 팀원이 반드시 한 명은 있다. 실패 시 UI 로 알린다.

**게임플레이**

- **★ 감쇠 `FalloffMode` 기본값(`Continues`)을 그대로 두면 경계에서 목소리가 뚝 끊긴다.**
  클라는 계속 들리려 하는데 서버가 송신을 멈추기 때문이다. `Silent` 로 바꿔서
  **클라 감쇠가 0 이 되는 거리와 서버 컷 거리를 맞춘다**(7-2절).
- **감쇠 반경을 하나의 숫자로 착각하지 말 것.** `Radius`(100% 구간) + `FalloffDistance`(감쇠 구간)
  두 개이고, 가청 거리는 그 **합**이다. 13절 표의 숫자를 에셋에 그대로 넣으면 사거리가 2배가 된다.
- 사망자 차단을 클라이언트에만 두면 뚫린다. **서버 3중 방어**(8절).
- 소음 이벤트를 프레임마다 쏘면 서버가 죽는다. 집계 창 필수(7-5절).
- `Instigator` 를 잘못 넣으면 NPC 가 엉뚱한 사람을 쫓는다(7-5절).
- **라우트 우선순위를 빼먹으면 가까운 사람 목소리가 두 번 겹쳐 들린다**(7-3절).

**프라이버시 (팀 프로젝트라도 명시한다)**

- **음성을 디스크에 저장하지 않는다.** 녹음 기능을 만들지 않는다.
- 마이크가 열려 있는 동안 **화면에 항상 표시**한다.
- 채팅 비밀번호 규칙과 같은 급으로 다룬다 — 음성 데이터를 `UE_LOG` 에 덤프하지 않는다.

## 16. 나중에 (지금은 안 한다)

우선순위가 낮아 이번 범위에서 뺀 것들. **설계에 자리는 비워 두되 구현하지 않는다.**

| 항목 | 왜 미루나 | 나중에 붙이는 법 |
|---|---|---|
| **이어폰 아이템** | 우선순위 최하위 | `URadioComponent` 에 `bEarpiece` 추가 → true 면 무전 재생을 2D 로 돌리고 `SpeakerNoiseRadius` 를 0 으로 |
| **무전 채널 (주파수)** | 인원이 적어 채널을 나누면 무전이 무의미 | 레지스트리를 `TMap<int32, TArray<...>>` 로 바꾸면 끝. 라우팅 코드는 그대로 |
| **립싱크 애니메이션** | 연출이고 게임 규칙이 아님 | `Loudness` 를 애님 BP 에 전달 (값은 이미 있다) |
| **NPC 반응 로직** | **NPC 담당 팀원 영역** | 우리는 `ReportNoiseEvent` 까지. Tag 로 분기(7-5절) |
| **사망자 텍스트 채팅** | 기존 `Dead` 채널 재사용 가능 | 신원 미러링(8단계) 먼저 (8-1절) |
| **무전 중계기 / 전파 방해** | 맵 디자인이 정해져야 함 | 무전 라우팅에 조건 하나 추가 |
| **잡음 제거 (Krisp 등)** | 아래 ★ | 캡처 직후 · 인코딩 직전에 한 단계 끼운다 (`FVoiceCaptureSource::Poll` 과 `FMOUVoiceEncoder::Encode` 사이) |

> **★ 잡음 제거를 지금 넣지 않는 이유.**
> 실제로 겪은 문제("가만히 있는데 계속 말하는 중")는 잡음 제거가 아니라
> **감도 보정**으로 해결되는 문제였다(`MOU.Voice.Calibrate`). 잡음 제거는
> 그 위에 얹는 품질 개선이지 대체재가 아니다 — 게이트를 못 맞춘 상태에서
> 잡음 제거를 넣으면 원인이 두 겹으로 가려진다.
>
> 넣게 된다면 **끼울 자리는 이미 명확하다**: 20ms PCM 프레임이 만들어진 직후,
> 인코딩 전이다. RMS/VAD 계산도 그 뒤로 옮겨야 한다 — 잡음을 지운 뒤의 음량으로
> 판정해야 게이트가 훨씬 잘 맞는다.
>
> 다만 Krisp 는 **상용 SDK 라 라이선스와 배포 조건을 먼저 확인해야 한다.**
> 무료 대안으로는 RNNoise(BSD)가 있고, 같은 자리에 같은 방식으로 붙는다.

### 17-1. 확인 완료 (UE 5.8, 2026-08-13)

V0·V1 을 구현하면서 아래는 **엔진 헤더에서 직접 확인했다.** 실제 서명 그대로 적는다.

| API | 확인된 서명 / 사실 |
|---|---|
| 캡처 생성 | `FVoiceModule::Get().CreateVoiceCapture(const FString& DeviceName, int32 SampleRate, int32 NumChannels)` → `TSharedPtr<IVoiceCapture>` |
| 데이터 회수 | `IVoiceCapture::GetVoiceData(uint8* Out, uint32 BufSize, uint32& OutAvailable)` → `EVoiceCaptureState::Type` |
| 캡처 상태 | `EVoiceCaptureState`: `UnInitialized / NotCapturing / Ok / NoData / Stopping / BufferTooSmall / Error` |
| **샘플레이트 제약** | **8000 ~ 48000 Hz.** 벗어나면 경고 후 실패 (`VoiceCaptureWindows.cpp`). **16000 은 안전** |
| 신스 초기화 | `virtual bool Init(int32& SampleRate)` |
| 오디오 생성 | `virtual int32 OnGenerateAudio(float* OutAudio, int32 NumSamples)` — 채운 샘플 수를 반환 |

| 링버퍼 | `Audio::TCircularAudioBuffer<float>` — `DSP/Dsp.h`. **SPSC 전용** |
| 소음 이벤트 | `UAISense_Hearing::ReportNoiseEvent(UObject* WorldContext, FVector Loc, float Loudness=1.f, AActor* Instigator=nullptr, float MaxRange=0.f, FName Tag=NAME_None)` |
| 감쇠 거리 모델 | `EAttenuationDistanceModel`: `Linear/Logarithmic/Inverse/LogReverse/NaturalSound/Custom` |
| 감쇠 폴오프 모드 | `ENaturalSoundFalloffMode`: `Continues`(기본) / `Silent` / `Hold` ← 7-2절의 함정 |

**함정으로 밝혀진 것 두 가지**

- `ULocalPlayer` 에는 인자 없는 `GetPlayerController()` 가 **없다.**
  (그건 `FLocalPlayerContext` 의 것이다) `UPlayer::GetPlayerController(const UWorld*)` 를 쓴다.
- `USynthComponent::Start()` 는 `IsActive()` 면 즉시 반환하므로 **두 번 불러도 안전하다.**
  `bAutoActivate` 와 명시적 `Start()` 가 겹쳐도 `Init()` 은 한 번만 불린다.

### 17-2. 확인 완료 (V2, 2026-08-18)

V2 를 구현하며 엔진 소스에서 직접 확인했다. **자세한 것과 함정은 14-4절.**

| API | 확인된 서명 / 사실 |
|---|---|
| 인코더 생성 | `FVoiceModule::Get().CreateVoiceEncoder(int32 SampleRate, int32 NumChannels, EAudioEncodeHint)` → `TSharedPtr<IVoiceEncoder>` |

| 디코딩 | `void Decode(const uint8* In, uint32 InSize, uint8* OutPCM, uint32& OutSize)` — 역시 in/out. **단위가 샘플이 아니라 바이트** |

| 인코더 기본값 | VBR ON / 제약VBR OFF / 복잡도 1 / FEC OFF. **비트레이트는 미설정** → 우리가 `SetBitrate` 로 명시 |
| 샘플레이트 제약 | 인코더/디코더 모두 8000·12000·16000·24000·48000 만. **16000 은 안전** |

### 17-4. 아이템·캐릭터 파트에 확인/요청할 것 (V9, 2026-08-20)

**음성 파트가 혼자 해결할 수 없는 것들이다.** 위 두 개는 요청해야 한다.

| # | 확인/요청할 것 | 대상 | 왜 필요한가 |
|---|---|---|---|
| 1 | **장착 시 캐릭터에 Attach 해 주기** | 아이템·캐릭터 | `GetHolder()` 가 부착으로 주인을 찾는다. 없으면 **무전 송수신이 통째로 안 된다** ← **최우선** |
| 2 | **사망·기절 시 `Drop()` 을 태워 주기** | 캐릭터 | 안 그러면 전원이 켜진 채 남아 배터리가 계속 닳는다 (소리는 라우터가 막으므로 안 난다) |
| 3 | 무전기 소지 개수 정책 | 아이템 | 라우터가 재생은 막지만, **두 대를 갖는 것 자체**를 막을지는 아이템 파트 결정 |
| 4 | `CurrentDurability` 를 배터리로 써도 되는지 | 아이템 | 아이템 파트가 이 값을 "내구도" 로 따로 쓸 계획이 있으면 충돌한다 |
| 5 | 인벤토리 아이템에 `OnUse` 를 연결할 계획이 있는지 | 아이템 | 현재 `AMainCharacter::OnUse` 는 `TODO` 상태. 연결되어도 무전기는 좌클릭을 안 쓰므로 영향 없음 |

> **1번을 기다리는 동안의 대안은 `AVoiceDebugRadio` 다.** 스스로 attach 하므로
> 무전 파이프라인 자체(라우팅·반이중·톤·NPC 소음)는 지금도 콘솔로 검증된다.
> 검증할 수 없는 것은 **아이템 조작 경로**(줍기 → 장착 → 인벤토리 → 드롭)뿐이다.
